### The Rayzor logs, and what 191 wasted requests actually meant

LOG18 (405KB, three Elation Proteus Rayzor 1960 on a **direct** link, no wireless proxy) and LOG17 (an Elation KL CORE IP acting as a genuine proxy, `PROXIED_DEVICE_COUNT`=3) were finally analyzed. LOG18: **516 requests, 516 responses, 293 ACK, 223 NACK** — no drops, so nothing here is a link problem.

The NACK breakdown is the finding. **191 `UNKNOWN_PID`, every one of them Benny512 GET-probing a PID the fixture never advertised in `SUPPORTED_PARAMETERS`** — the E1.37-1 dimmer set at 22 each, `PROXIED_DEVICE_COUNT` ×25, `PRODUCT_DETAIL_ID_LIST` ×30, `IDENTIFY_MODE` ×22, `STATUS_MESSAGES` ×4. The counts reconcile exactly (25+4+30+110+22 = 191). The app was asking every device the same fixed list of interesting questions regardless of what that device said it could answer.

The other **32 are `FORMAT_ERROR`, and they are two genuine bugs**: `RESET_DEVICE` was being issued as a **GET** 24 times (it is SET-only), and `SLOT_DESCRIPTION` was GET'd 8 times with PDL=0 when its GET requires a 2-byte slot number. Both are now blocked at the source in `getRaw()` rather than filtered downstream.

Worth recording because it inverts an earlier reading: this NACK volume had been noted before as "consistent with healthy feature-detection." It isn't. It is roughly 40% of all traffic to a device spent asking questions we already had the answer to — which matters far more on the congested CRMX link than on the direct one where it was measured.

The Rayzor's actual `SUPPORTED_PARAMETERS` (16 PIDs): device/manufacturer/model labels, `FACTORY_DEFAULTS`, `DMX_PERSONALITY`(+description), sensors, `DEVICE_HOURS`, `LAMP_HOURS`, `LAMP_STATE`, `DISPLAY_INVERT`, `SLOT_DESCRIPTION`, `PAN_INVERT`, `TILT_INVERT`, `RESET_DEVICE`. Notably it has **no E1.37-1 dimmer-curve support at all** — Dom's own leading example of a promote-worthy PID isn't present on the fixtures in this capture, which is exactly why he flagged the Rayzor as illustrative rather than exhaustive, and why the classification could not be reverse-engineered from it.

### PID classification — a table, not a curated list

`internal/params/classification.go`: three tiers — `TierPromoted` (dedicated control in the base UI), `TierStandard` (generic parameter list), `TierHidden` (never rendered as a row) — behind `Tier(pid rdm.ParameterID) PIDTier`, backed by a map keyed on the existing `rdm.ParameterID` constants.

**The design decision that matters is the fallback: an unrecognized PID is `TierStandard`, never `TierHidden`.** Hiding by default would silently swallow real, spec-defined data from a fixture we've never seen — a future E1.37 addendum, or the next thing Dom plugs in. Hidden is explicit opt-in only, and a test asserts an arbitrary unknown PID lands in Standard. Adding a PID later is a one-line map entry; *not* adding it costs nothing. That property is the whole point, given Dom explicitly expects to request more.

Promoted, per Dom's own selections: the existing four (device label, DMX address, personality, identify), the dimmer set that already had fields, the **service-life family** (device hours, lamp hours, lamp strikes, lamp state, power cycles), **pan/tilt invert and swap**, **display invert and level**, and the two destructive actions (`RESET_DEVICE`, `FACTORY_DEFAULTS`). Hidden: the discovery PIDs, proxied-devices pair, comms status, queued/status message family, the introspection machinery (`SUPPORTED_PARAMETERS`, `PARAMETER_DESCRIPTION`, the enhanced/packed variants), `DEVICE_INFO`, `PRODUCT_DETAIL_ID_LIST`, sensor definitions, and the E1.37-2 / E1.33 / E1.37-7 PIDs that have their own dedicated surfaces.

The tier ships to the browser as a `tier` field on each parameter descriptor, so **no client-side PID list decides visibility** — Dom's future additions need no JS change at all.

**A prior decision had to be deliberately reversed.** `introspect.go` carried a comment documenting an earlier task that *intentionally* made `PROXIED_DEVICES`/`PROXIED_DEVICE_COUNT` visible in the editor, because the UI had dropped its dedicated proxy callout and this was the only remaining way to see them. Dom now names those exact PIDs as things a user shouldn't see. Rather than just delete the information, the pair is hidden as rows and proxy status returns as structured device-level data (`proxiedDeviceCount`, `proxiedDeviceCountKnown`, `proxiedListChanged`) rendered as a badge — "Proxy — 3 devices". Fixing the reason the earlier decision existed, instead of only reversing it.

Fixing that also corrected the wire decode: `PROXIED_DEVICE_COUNT` is a UINT16 count plus a one-byte "list changed" flag per E1.20 §8.4.1, and the old code checked `len(data)>=2` and ignored the flag entirely.

### Warm and cold reset — and being honest about what can't be known

Verified directly against ANSI E1.20-2025 §10.11.2 (p.113), read in the PDF rather than recalled: `RESET_DEVICE` is **0x1001, SET_COMMAND only**, PDL 1, PD **0x01 = warm**, **0xFF = cold**. Spec text: *"This parameter is used to instruct the responder to reset itself. This parameter shall also clear the Discovery Mute flag. A cold reset is the equivalent of removing and reapplying power to the device."* `FACTORY_DEFAULTS` (0x0090) was separately verified: GET returns a one-byte "are settings currently factory default", SET takes PDL=0.

**There is no way to discover whether a given fixture actually distinguishes warm from cold.** `SUPPORTED_PARAMETERS` says only whether 0x1001 is listed; `PARAMETER_DESCRIPTION` is spec-legal for manufacturer-specific PIDs only, so it cannot help; and the only way to learn the difference empirically is to send it, which is destructive by definition. So both buttons are offered whenever the PID is advertised, and the UI says plainly that a fixture may treat them identically. Arm-then-confirm protects against a misclick; it cannot protect against a fixture that cold-resets whichever button you press, and claiming otherwise would be a false reassurance on show hardware.

The Discovery Mute consequence is handled rather than ignored: a successful reset drops the device's cached state (`ForgetDevice`), and the UI tells the user the fixture will need re-discovery.

Both actions sit behind the established arm → confirm → 8-second auto-disarm pattern, with the confirm naming the specific device, and the server additionally requires a `{"confirm":"RESET"}` body so it is never one stray request from resetting a fixture.

### The sorting bug — and the defect class behind it

Dom: *"When sorting by Universe + address, devices on universe 1, 2, and 3 are out of order and intermingled in with the rest of the patch, but universes over 10 organize correctly."*

His exported patch spans universes 1,2,3,11,12,13,21,22,23,31,32. A lexicographic sort of that set gives 1,11,12,13,2,21,22,23,3,31,32 — teens and twenties grouping correctly while 1, 2, 3 scatter, matching his description exactly. **That diagnosis was wrong.** The comparator was already numeric (`a.universe - b.universe`).

**The real cause:** `patch.Entry` declared `Universe uint16 \`json:"universe,omitempty"\``. `omitempty` on a numeric field **erases a legitimate zero** — so an entry at canonical universe 0 (displayed "1" at Dom's default base) had its `universe` key omitted from the JSON entirely, arrived client-side as `undefined`, and `undefined - n` is `NaN`. `Array.prototype.sort` with a NaN-returning comparator has unspecified behavior; V8 leaves the pair unswapped, quietly displacing exactly the low-universe entries.

Two things about this are worth keeping. First, it only reproduces when the affected entry's position in the array isn't already correct — a first repro attempt that inserted entries in ascending order looked clean and proved nothing. The verified reproduction shuffles insertion order. Second, and more important: **this project's own Notes already recorded this exact defect** during Phase 1c+ — `sensorReadingJSON` using `omitempty` on range fields so "a legitimate `0` is *absent* from the JSON", worked around client-side at the time. The workaround left the cause in place, and the same mistake was independently made again on a different struct. On inspection the original fix was incomplete too: `HasRange`/`HasNormalBand` flags were added but the `omitempty` tags stayed.

So this round fixed the class rather than the instance. A full audit of every JSON-serialized struct in `internal/patch` and `internal/web` removed `omitempty` from every numeric field whose zero is real data — entry universe/startAddress/footprint (a zero footprint is meaningful: it's what an unresolved GDTF import produces and what the collision detector reports on), collision finding universe/channelStart/channelEnd, the sensor range/normal bounds from the original 1c+ finding, param int value, service-life value, devices-clear portAddress, fixture deviceModelId/proxiedDeviceCount, and fixAll applied. Genuinely optional strings keep `omitempty`; each field's decision is recorded per-field rather than swept.

**The audit found two more live bugs nobody had reported yet.** `collision.Finding.Universe` is read by `composeFindingMessage` with no guard, so a collision in universe 0 would have produced wrong banner text. And `fixAllResponse.Applied` omitted at zero rendered as *"fixed undefined of N"* whenever every SET in a fix-all failed — the message you'd see precisely when something had gone wrong.

Every new test asserts on **marshalled JSON bytes**, not struct fields — `len==0` and `field == 0` are both true for the bug and would pass vacuously. Each was proven to fail against the unfixed code by restoring the tags and capturing the failure output.

Also flagged, outside the audited packages and left for their owner: `capture.RDMDetail.NackReasonCode` (RDM's `NR_UNKNOWN_PID` *is* 0x0000 — a real and common value) and `TodDetail.UidTotal` (an empty rig is legitimately 0).

### Port grouping moved to the Nodes screen

Nodes now groups by IP — same reasoning as before, since a real EN4 sends one ArtPollReply per physical port with its own bind index, so grouping by `NodeKey{IP,BindIndex}` would still split one box into three — and sorts devices by IP **numerically** via octet comparison, ports by port-address numerically. **A nasty bug was found and fixed during that work.** The first implementation auto-selected a device's first port from a `<details>` `toggle` listener that called `render()`. The listener is now state-only and the convenience moved to the `<summary>` click (a real user gesture), with a `ROOT CAUSE` comment so it isn't reintroduced.

### E1.20 §10.11 — all device control messages

Enumerated from the spec itself (PDF pages 128–138, cross-checked against Appendix A Table A-3) rather than from memory, because two of these are destructive on show hardware:

| PID | Name | § | CC | Notes |
|---|---|---|---|---|
| 0x1000 | IDENTIFY_DEVICE | 10.11.1 | GET/SET | already implemented |
| 0x1001 | RESET_DEVICE | 10.11.2 | **SET only** | already implemented (0x01 warm / 0xFF cold) |
| 0x1010 | POWER_STATE | 10.11.3 | GET/SET | Table A-11 enum: FULL_OFF 0x00, SHUTDOWN 0x01, STANDBY 0x02, NORMAL 0xFF |
| 0x1020 | PERFORM_SELFTEST | 10.11.4 | GET/SET | Table A-10: 0x00 OFF, 0x01–0xFE manufacturer tests, 0xFF ALL |
| 0x1021 | SELF_TEST_DESCRIPTION | 10.11.5 | GET only | indexed: request carries the test number, response is number + ≤32-byte label |
| 0x1022 | SELFTEST_ENHANCED | 10.11.8 | GET only | packed 6-byte entries, ACK/ACK_OVERFLOW |
| 0x1030 | CAPTURE_PRESET | 10.11.6 | **SET only** | PDL 2 or 8: scene, optionally + up-fade/down-fade/wait |
| 0x1031 | PRESET_PLAYBACK | 10.11.7 | GET/SET | Table A-7: mode16 (OFF 0x0000 / ALL 0xFFFF / scene) + level8 |

Note §10.11.8 sits *after* 10.11.6/10.11.7 in the numbering but belongs to the same section — worth recording, since an implementer reading only 10.11.1 through 10.11.7 would silently miss `SELFTEST_ENHANCED`.

Enum PIDs render as labeled choices because the *spec* defines those labels. That is not a departure from this project's standing rule that `PARAMETER_DESCRIPTION` carries no per-value enum labels and therefore unknown enumerated fields must be bounded numeric steppers — the rule is about manufacturer PIDs whose labels are genuinely unknowable; here the labels are normative.

**Arm-then-confirm gating, and the reasoning:** POWER_STATE (can leave a fixture unresponsive), each self-test run (swings a fixture through its full motion range — disruptive mid-show even though it isn't destructive), CAPTURE_PRESET (irreversibly overwrites stored scene data), PRESET_PLAYBACK (changes the live look). Turning a self test *off* is deliberately ungated: it is the remedial direction, and making the fix harder than the mistake is bad design.

**Flagged rather than guessed:** `SELFTEST_ENHANCED`'s manufacturer-specific result codes are resolved via `ENUM_LABEL`, which this codebase does not implement anywhere. The result-code PID and value are decoded and preserved but not resolved to text. Inventing labels there would have been the exact failure this project's rules exist to prevent.

### E1.37-2 network configuration — built to be *disproved*

This is the segment Dom's morning bench session exists to settle, and it was built under an unusual constraint worth recording: **primary E1.37-2 text was unavailable.** The specification was a Claude project file and project access is disabled in this session; the derived research document lives on Dom's machine, which was asleep. So the ground truth for this feature was `internal/params/ipconfig.go`, whose own doc comment says it *"follows the OLA-style interface-ID-prefixed convention, not primary E1.37-2 text."*

The decision taken, deliberately: **build no new wire-format guesses.** Everything shipped traces to bytes `ipconfig.go` had already committed to. Where no confirmed layout exists — `INTERFACE_HARDWARE_ADDRESS_TYPE1`, `IPV4_ZEROCONF_MODE`, `IPV4_DEFAULT_ROUTE`, and writing `DNS_NAME_SERVER` — nothing was built rather than something plausible. Absent by design beats silently stubbed, and a guessed IP-config layout can strand a gateway off a show network.

Survey findings worth keeping: `ipconfig.go` already had typed methods for 9 of the 14 E1.37-2 PIDs; all the PID constants existed; all were `TierHidden`; `internal/capture/rdmdetail.go` had **name lookup only, zero byte decoding**; and `internal/web` exposed nothing at all. So the plumbing was largely present and had simply never been surfaced or exercised.

What shipped: `internal/web/network.go` with per-interface GET plus static-address, DHCP and DNS writes; a "Network configuration (E1.37-2)" panel on the device detail pane with per-interface arm-then-confirm matching the Nodes IP editor; client-side *and* server-side IPv4/netmask validation (defense in depth — a malformed address is rejected in the browser and again at the endpoint); graceful absence on the overwhelming majority of devices that don't implement any of this; and a caution banner stating plainly that the layouts are unverified and that a mis-set address can strand a device. Dom is a non-programmer relying on the UI to tell him the truth about its own confidence.

**The design goal was a decisive log, not a working feature.** `rdmdetail.go` now renders human-readable decoding *alongside* raw hex for every E1.37-2 PID, and explicitly labels the three unconfirmed-layout PIDs "UNCONFIRMED" rather than pretending. A real captured line:

```
PID=0x0706 (IPV4_STATIC_ADDRESS)  PDL=12
decoded: SET interface=1 ip=2.11.90.77 mask=255.255.0.0
paramData: 00000001020b5a4dffff0000
```

A GET → SET → GET-back round trip is now readable by hand, which is what proves or disproves the format. A bench procedure written for a lighting professional rather than a programmer lives at `E1372-BENCH-TEST.md`: what to click, in what order, what to watch on the device's own panel, and what an ACK-but-nothing-changed versus a NACK versus silence each imply. Its most important instruction is that `INTERFACE_APPLY_CONFIGURATION` returning ACK **does not prove the device applied anything** — RDM offers no stronger signal, so the front panel is the only ground truth.

Also fixed while in `rdmdetail.go`: `NackReasonCode` carried `omitempty`, which would have erased `NR_UNKNOWN_PID` (0x0000) — a real and common reason code — from the JSON. That was on the open-items list from the previous entry as an outstanding instance of this defect class; it is now closed, with a regression test asserting the marshalled bytes.

### A "flaky test" that was really a test hang, found only by refusing to accept a clean report

This is the most instructive part of the night.

Two verification passes reported clean. But the orchestrator's own repeated runs produced `--- PASS` counts of 658, 657, and 656 across three runs. Chasing that variance rather than shrugging at it revealed **one test failing on nearly every run, and a different test each time** — rotating among `TestGetDeviceControl`, `TestPatchReconcile_MatchedAndMissing`, `TestResetDeviceSucceedsWithConfirmation`, `TestCapturePresetRequiresConfirmationAndValidatesScene`, `TestGetServiceLife`, `TestDeviceActionsReportsAdvertisement`. A rotating victim is the signature of a shared resource, never of one bad test.

The failure message was itself misleading in a useful way: *"timed out waiting for HTTP handler to resolve (no progress after many fake-clock advances — a real hang, not scheduling jitter)."*

**Root cause:** `runHTTPAsync` — the helper behind roughly 90% of `internal/web`'s HTTP tests — drove the fake clock with a fixed 20,000-iteration spin: `select { default: Advance(2ms); runtime.Gosched() }`. A goroutine-stack dump captured at the moment of a hang showed the HTTP handler goroutine still `[runnable]`, parked at the very first line of `httptest.NewRequest`, never having been scheduled once, while the driving goroutine had already burned its entire budget. `runtime.Gosched()` *offers* the scheduler a chance to run another goroutine; it guarantees nothing. On a contended two-core box, 20,000 cheap iterations complete in low single-digit milliseconds — faster than the handler goroutine got a single timeslice.

The fix is genuinely deterministic rather than merely less likely to lose: a new `FakeTransport.SentSignal()` channel fires the instant a datagram is recorded, and the helpers now `select` on completion, that signal, and a 1 ms real ticker, **with no iteration cap at all**. The driving goroutine blocks for real — costing no CPU — so the handler gets whatever scheduling time it needs. A 30-second timer survives purely as a deadlock backstop for a genuine production hang, never as part of the passing path.

A second, smaller isolation gap was closed alongside it: `internal/params`' process-wide descriptor cache and per-UID introspection state were never reset between tests, and several test files reuse identical UID literals. `newHarness` now clears both via `t.Cleanup`.

Verified across 25 full-suite runs, 25 `internal/web` runs, 22 under `-race`, 20 under `-cpu=1`, and 20 under artificial CPU load — zero failures. Then independently re-verified by the orchestrator in its own session: **ten consecutive runs, 658/658, zero failures.**

Two lessons worth carrying, both already reflected in the handoff. First: **a varying test count is a defect report, not noise** — the earlier convention of quoting a single run's count would have shipped this. Second: this is the fourth time a "verified clean" subagent report has been wrong in a way only repeated or cross-cutting checking caught, which is precisely why the orchestrator re-verifies rather than trusting.

An earlier pass in the same night had already rewritten several *other* real-clock-vs-fake-clock polling loops (`device_test.go`'s introspect and proxied-count tests, `node_config_test.go`, `session/nodeconfig_test.go`) that raced a wall-clock deadline against fake-clock advances — the defect the Phase 2a notes characterized and deferred. Those are now bounded-progress loops too. The Phase 2a flaky-test note can come off the open list.

### The footprints were never a parser bug — and this is the most useful finding of the night

The previous session recorded 61 and 23 as correct, with the last channel explained away as "designer padding". That explanation was never tested, and the fixture comment recording it *contradicted the only independent measurement it cited* (real address spacing of 62 and 24).

Dom supplied the real vendor files. Run against them the existing parser is **already correct on every mode, first try**: all eleven Paladin Cube modes (including `Cells 24CH` → 24, built from 16-bit `Offset="1,2"` pairs) and all six JDC1 modes (`Mode 4 SPix PRO (62ch)` → 62, which needs the GeometryReference walk to reach past a literal max offset of 51).

The MVR is the culprit. Vectorworks writes **placeholder GDTF stand-ins** into an MVR for fixture types it has no real profile for:

| | JDC1 | Paladin Cube |
|---|---|---|
| `Custom@Light_Instr_*` inside the MVR | one generic `DMX Mode`, 61 flat channels | one generic `DMX Mode`, 23 flat channels |
| real vendor file | 62 ✅ | 24 ✅ |

Both placeholders also carry a vestigial 8-channel `Default` mode with no offsets. The other three types in the show (ERA 800, Rayzor, Rogue Outcast) ship genuine manufacturer GDTFs in the same MVR, which is exactly why only these two were wrong. **Benny512 was faithfully parsing a lossy file.**

A hypothesis worth recording as dead: the leading theory going in was that a trailing `NoFeature` channel was being excluded from the footprint. It is not — the parser has never filtered by attribute name, only by `Offset`. Probed directly on identical modes: trailing `NoFeature` with `Offset="62"` → 62; with `Offset="None"` or no `Offset` → 61. "Has no function" and "does not exist" were already correctly distinguished. Counting virtual (offset-less) channels to "fix" the two disputed fixtures would have broken four independently corroborated JDC1 modes whose names state their own counts.

So the fix is **provenance, not arithmetic**. `gdtfparse.js` now detects the placeholder shape and warns through the existing warnings channel, with four independent guards against false positives — channel count, mode name, structure, manufacturer — because a warning that fires on a real 4-channel LED par trains Dom to ignore warnings. Verified against the actual files: both placeholders flagged exactly once; real Elation (including its genuine `RGB 3CH` and `8bit 4CH` modes) and real GLP raise nothing. A separate mode-name channel-count cross-check (`(62ch)`, `62 Ch`, `62-Channel`) is used strictly as an **oracle that raises a warning, never as parser input** — a mode name is unvalidated free text, and a fixture patched at a footprint no channel occupies is silently wrong on the wire.

### Fixture Library

`internal/library`: one record per **manufacturer + model** with modes nested inside (Dom's choice over a flat type-and-mode key), holding RDM manufacturer and device model IDs, observed supported PIDs, and per-mode footprint and channel map — reusing `patch.ChannelFunction` rather than defining a parallel type, so it inherited the new default fields for free.

Persisted separately from any show patch, which is the point: Dom runs Benny512 on multiple unrelated rigs and wants a patch file per rig over a library that persists underneath. Exportable and importable as one self-identifying JSON document (`format` + `schemaVersion`, so a patch export handed over by mistake is rejected rather than silently imported as an empty library), records sorted by key so the file diffs cleanly, per-piece provenance rather than one record-level lie.

**The reset exemption is structural, not conventional.** `library.Store` deliberately has no `Clear()` method — the method a reset would need does not exist. That property was preserved when the store was later moved onto `Server` as a proper field, because the first implementation held it in a `sync.Map` keyed by `*Server` specifically so `handleReset` could not reach it, and moving it would otherwise have downgraded an impossibility to a comment. Both halves are now in place: the field, and the missing method.

Two directions of travel: harvest a patch entry's profile **into** the library, and **re-profile** patch entries from it. The second is Dom's repair path for the placeholder problem — fix an already-imported patch in place rather than re-importing the MVR. It changes DMX addressing on a real show patch, so it requires explicit confirmation, reports old→new footprint per entry, and runs collision detection afterwards, reporting findings without blocking. Dom decides.

Caught and fixed during this: `SetLibraryStorePath` existed and was tested but was never called at startup, so in production the library was in-memory only and lost on every restart — defeating its entire purpose. A test now constructs a store, writes records, drops it, and reconstructs from the same path.

### Rig Check: a selection, and an output flag, and nothing else

The tilt-to-maximum was two defects compounding. The engine drove one pattern at a time; the client had its own idea of what was selected; and the old engine deliberately **zeroed every channel it wasn't testing** — a documented past decision ("never a 'helpful' implicit dimmer-up or shutter-open") that Dom is right to reverse, because a real fixture needs both a dimmer at level *and* a shutter in its open position to emit light. Testing a dimmer produced one flash and darkness.

Dom's decision, implemented: every channel no active test drives goes to its **GDTF `Default`** value; dimmer to full and shutter to open **only when no active test already drives that channel**. Finding "shutter open" is the honest-judgment part — a ChannelSet whose name reads open and not closed/strobing, else the channel's own GDTF default, and where neither exists **the channel is left at 0 and the fixture is named in `baseState.shutterUnknownEntries`** rather than being given an invented value. Today's zero-everything behaviour survives as an explicit **isolate** mode, off by default, because proving which channel drives which function is what it was actually good for.

The state model is now two independent things: a **selection** of tests with their parameters, and an **output-enabled** flag. Start opens the gate; stop closes it; scope, tests, parameters and isolate are all editable either side of it, exactly as Dom specified. Multiple patterns compose in a **fixed canonical order** (group, then kind, then target) rather than toggle order, so the same set of tests always produces the same frame regardless of click sequence, and every contested DMX offset is reported with the winner named.

New: **waveform** as a property of every continuous test (`sine` or `snap`) rather than a separate kind, so snap composes with everything. **Phase offset in degrees**, spread MA3-style — fixture *i* of *n* gets `min + (max-min)·i/n`, divisor *n* not *n−1*, so 0–360 across eight fixtures puts the last at 315° and the chase wraps seamlessly; 0–720 gives two cycles, which is what Dom described. Rejected with a 400 on static kinds rather than half-applied. **Gobo wheel step and rotate**, enumerated per wheel the fixture actually has. And **frost enumerated per `Frost*` function** — replacing a `Target` of `""`/`"light"`/`"heavy"` resolved by a heuristic the code itself flagged as a judgment call. The app now says what GDTF says and lets Dom read the label; it does not decide which filter is the light one.

The stale-UI bug was killed on both sides. Every mutating endpoint returns the **complete status snapshot**, and the client's only state is the last server response — `snap = await fn(); render()`, with an error re-reading the server rather than painting the attempt. Leaving the screen and returning repaints from the server, which is the cheapest available proof that no local mirror survives.

The screen is a toggle tile per available test, grouped by attribute, extracted to `rigcheck.js`. Tablet-first because that is where it is used: 44px minimum targets, START and STOP always present and always in the same place, and on/off carried by icon, word and border weight as well as colour. **The test list is never hardcoded** — it is `available[]`, whatever the fixtures currently in scope actually support, which is how Frost Light and Frost Heavy appear as two tiles on a fixture with two frost filters.

### Reconcile had no verbs

Diagnosed by driving the old screen and dumping every button in every group rather than by reading code: of 14 rows, **12 offered no action at all**. `matched`, `missing` and `unpatched` all rendered an empty action list. The only route to a stored `ConfirmedUID` was an `ambiguous` row's candidate list (zero such rows in demo) or "Fix device address" — which fires an RDM SET as a side effect, so it was impossible to record that a light was the right light without writing to it. **Decommit did not exist in any form**, which blocks substitution entirely. The matcher was fine; the screen was a read-only report of its score.

Now two panes — what the patch says should be there, and what actually answered — with commit and decommit as the verbs. Per Dom's decision, **commit records and never writes**: it stores the UID, reads the fixture's settings as-found, and shows a per-setting diff against intent, with each difference pushed only on its own explicit press.

Every stored reading carries a `Known` flag, its own read time, and the fixture's own error text — so a value of 0 is never confused with never having asked, "as-found in the shop three weeks ago" is distinguishable from "as-found ten minutes ago on site", and "this fixture has no dimmer curve" reads as a fact about the fixture rather than a bug in the app. Per-field timestamps rather than one per entry, because a commit that reads the address but NACKs the curve genuinely produces two read times.

**The substitution guard is the part worth keeping.** The as-found block stores the UID it was read from, and the diff discards the whole block if it disagrees with the committed UID. Commit a replacement onto an entry still carrying the dead fixture's readings and every field reads *unread*, never *match*. A green all-clear against a light that is no longer in the truss is the one failure this screen must never produce.

An "adopt as intended" direction had to be added: "take on all the old settings of the original fixture" is unimplementable otherwise, because dimmer curve and the pan/tilt inverts had no home on `patch.Entry` at all. Adopt writes to the patch only and is deliberately not confirmation-gated; push writes to a fixture and is. In the shop you adopt; on site you apply.

Two defects were caught by **looking at the screenshots**, which no assertion found: the Apply button rendered outside the card at 1024×768, reachable only through a nested scrollbar, and icons rendered at ~100px because this component kit has no global SVG sizing rule and every component sizes its own.

### The fifth instance of the seam defect — and the first that broke a feature outright

The cross-boundary pass found that `gdtfparse.js` emitted `defaultValue`/`highlightValue` while the server's `channelFunctionRequest` expected `default`/`highlight`. Because `internal/web`'s `decodeJSON` sets `DisallowUnknownFields`, this was not a dropped value — it was an **outright rejection**:

```
400 {"error":"json: unknown field \"defaultValue\""}
```

**Every `PUT` of a GDTF profile and every MVR import that resolved even one channel function failed.** The headline feature of the night, dead on arrival, in a build that passed 928 tests.

Both sides' tests passed throughout, and could not have done otherwise. The Go test built its request from the Go struct, so it could only ever prove the server agrees with itself. The Node test read the parser's output back using the parser's own key names, so it could only ever prove the browser agrees with itself. Neither ever looked at the other's bytes.

This is the **fifth** instance of one class on this project — the same value spelled two ways in two files, each half correct in isolation — after the collision banner vs table universe, the device-detail `addr 0` vs table `U1`, the detail panels not re-rendering on a base change, and `"Full Off"` vs `"Full off"`. The first four displayed a wrong number; this one broke a feature. All five were caught the same way: by a pass that owned none of the work and read the live API alongside the UI.

`gdtfparse_wire_test.go` is now the only shape of test that can catch this class: it runs the literal `gdtfparse.js` the browser loads, takes the literal object it produces, and feeds those exact bytes to the literal HTTP handler the browser posts to.

### RDM-LOG24 — the first capture of the Reconcile commit path on real hardware

Eight GLP JDC-1s (manufacturer `676C`), 23 minutes, 333 packets, 138 ACK / 26 NACK. The PID set is exactly `readAsFound`'s, so this is the commit path Dom asked for last week, running against real fixtures for the first time. **It worked** — Dom confirmed he committed all eight to their patch entries successfully, which also explains the 3–5 `DEVICE_INFO` fetches per device that first looked like a possible loop. Not a defect; that was the feature being used.

**Every one of the 26 NACKs is `UNKNOWN_PID`, and every one was avoidable.** The JDC-1's own `SUPPORTED_PARAMETERS` lists 21 PIDs. Benny512 asked it for four that are not on that list: `PAN_INVERT` ×9, `PAN_TILT_SWAP` ×9, `PRODUCT_DETAIL_ID_LIST` ×5, `PROXIED_DEVICE_COUNT` ×3. `TILT_INVERT` **is** listed and ACKed all nine times — which is correct, because a JDC-1 tilts but does not pan. Two of those PIDs are named in the earlier speculative-probe fix as already gated. The gate existed; `readAsFound` was written the night before and never went through it. New code, old lesson.

It matters more than the packet count suggests. On a hard line it is noise. Behind the CRMX/MoonLite2 proxy whose shared buffer three earlier logs document filling and then refusing unrelated devices, wasted requests are a genuine failure mode.

**The fix is not just quieter, it is more honest.** A third state joins read and unread: **`not_fitted`**. "This fixture has no pan" is a fact about the fixture, and the screen now says that instead of showing a NACK string next to "Not read". Two properties were deliberately protected:

- **Absence of a supported-parameter list means UNKNOWN, never not-fitted.** If we never fetched the list, or the fetch failed, every gate opens and the pass behaves exactly as before. Treating "we don't know what it supports" as "it supports nothing" would silently blank every field on a device whose introspection hadn't finished. A test pins this against that exact wrong fix.
- **E1.20 required PIDs are never gated**, because §10.4.1 says a device *shall not* list them in `SUPPORTED_PARAMETERS` at all — so their absence means nothing. `DMX_START_ADDRESS` is genuinely missing from the JDC-1's real list and must still be asked for. Another test pins that.

The substitution guard survives: as-found still stores the UID it was read from and the diff discards the block on mismatch, so a dead JDC-1's "no pan" cannot be inherited by its replacement.

### The Nodes universe defect — one report, two bugs

Dom: *"the universe values in Benny512 are displaying as 1 less than what the faceplate says,"* with the EN4 confirmed 1-based starting at universe 1.

`nodes.js` had **25 universe references and zero `UI.formatUniverse` calls** — the only screen in the app that never converted. That is the bug he could see. Underneath it was a worse one: what it printed was not the Port-Address but `outputAddress & 0x0F`, the **Universe nibble alone**. A 15-bit Port-Address is Net(7) : Sub-Net(4) : Universe(4), and the nibble equals the Port-Address only while Net and Sub-Net are both zero — true of his rig and of the demo. One port on Sub-Net 1 and Nodes would read "0" for the port Patch reads "17" for.

**A test asserting only "canonical 0 shows as 1" would have passed against a screen still wrong for every rig bigger than one Sub-Net.** The Sub-Net case is the one that actually pins it.

**The write path is the dangerous half, and it carried a real product decision.** ArtAddress carries ONE NetSwitch and ONE SubSwitch for the whole packet; only SwIn/SwOut are per port, and each is a 4-bit nibble. ## 2026-09-07 (00:02 ET) — `SUPPORTED_PARAMETERS` fetches now coalesce per fixture

`params.Client.resolveSupportedSet` had a real thundering-herd window. It read `supportedAttempted` under a read lock, released it, then performed the RDM GET and only afterward recorded the attempt. Concurrent speculative reads for one UID could all observe `false`, then queue duplicate `GET SUPPORTED_PARAMETERS` transactions behind the controller’s serialization. A waiting caller may still return early when *its own* context is canceled. A failed or canceled owner attempt retains the existing once-per-process behavior: later calls report unknown and continue to allow speculative probes rather than pretending a fixture supports nothing.

`TestResolveSupportedSetCoalescesConcurrentFetches` deterministically holds the first request while twelve callers arrive, then proves all get the advertised answer and exactly one `SUPPORTED_PARAMETERS` GET reached the wire. ### 2026-09-02 (late) — E1.37-2 verified against primary text: three confirmed wire-format defects, NOT yet fixed

The E1.37-1 and E1.37-2 standards became readable as Claude project files this
session, after several sessions in which they were unavailable. `ipconfig.go`'s
own doc comment had admitted its layouts were "this package's best reading of
the common E1.37-2 responder convention (matching how OLA's own e137_2

**The guesses were wrong on three counts.** All three are confirmed against
ANSI E1.37-2:2015 (R2021) including its Appendix B worked example, so no
hardware is needed to settle any of them — which retires the bench test that
has been pending since 2026-09-01.

1. **LIST_INTERFACES.** Spec §4.1: the response is a packed list of interface
   descriptors of **48 bits (6 bytes) each** — Interface Identifier (32-bit)
   plus Interface Hardware Type (16-bit, IANA ARP-PARAMETERS; 0x0001 =
   Ethernet). `DecodeInterfaceList` reads **4-byte** IDs and guards on
   `len(data)%4 != 0`.

   The guard cannot catch it. Appendix B's real two-interface response is
   PDL 0x0c — `00000001 0001 00000002 0001` — and 12 % 4 == 0, so no error
   fires and the decoder returns **three phantom interfaces**: 0x00000001,
   0x00010000, 0x00020001. Every subsequent per-interface GET then carries a
   bogus identifier and earns NR_DATA_OUT_OF_RANGE. Silently wrong on a real
   device, with the length check giving false assurance.

2. **IPV4_CURRENT_ADDRESS.** Spec §4.6: response PDL **0x0a** — interface ID
   (32-bit), IPv4 address (32-bit), **netmask as a ONE-BYTE PREFIX LENGTH
   (0-32)**, and a **DHCP Status byte** (Table A-3: unknown/active/inactive).
   `DecodeIPv4Config` requires **>=12 bytes** and reads the mask as a 4-byte
   dotted address, so a real 10-byte response is **rejected outright**, and
   the DHCP status — exactly what you want when a gateway comes up on an
   unexpected address — is discarded.

3. **IPV4_STATIC_ADDRESS.** Spec §4.7: GET response and SET request are both
   PDL **0x09** — interface ID + address + **1-byte prefix**. Appendix B sets
   10.0.0.32/8 as `00000001 0a000020 08`. `SetIPv4StaticAddress` builds a
   **12-byte** payload with a 4-byte mask, i.e. **Benny512 would have written
   a malformed SET to a real gateway.** The caution banner was earned.

Also newly available and still unimplemented, with layouts now confirmed:
IPV4_ZEROCONF_MODE (GET PDL 0x04 interface ID; SET PDL 0x05 interface ID + a
0/1 byte; unsupported interfaces return 0 on GET and NR_ACTION_NOT_SUPPORTED
on SET), plus IPV4_DEFAULT_ROUTE, INTERFACE_HARDWARE_ADDRESS_TYPE1 (EUI-48)
and SET DNS_NAME_SERVER.

### The encoder shipped in `a15c3b5` was not conformant

It was committed as "verified sACN data packet encoder" and the previous

### The architectural decision that matters

**sACN is NOT sent from `DMXOutputEngine.transmitLocked`.** Three reasons, each
verified in the code rather than assumed: `e.universes` is ONE GLOBAL SET shared
by Rig Check, the pattern engine and `/api/dmx`, so a second send there would
put every universe any screen ever started onto both protocols; `transmitLocked`
holds `e.mu` across a synchronous UDP write and `SendNow` is called from HTTP
handler goroutines, so a second write doubles lock hold time on every tick; and
while a pattern is live each universe is ALREADY transmitted twice per interval
(`recomputePatternLocked` calls `SendNow` and the engine ticks independently),
which naive dual-protocol sending would multiply.

Instead Rig Check owns a narrow protocol-aware output boundary,
`internal/patch/rigcheckout.go`. Exactly one protocol drives a given universe at
a time. **Selecting sACN takes the universe OFF Art-Net** -- it does not add to
it -- and switching runs the outgoing protocol's proper stop first. That is
proven by a real-socket test, not by reading code: it asserts Art-Net frames for
that universe actually stop, and that three Stream_Terminated packets go out on
the way back.

`stopLocked` became the single choke point, so the emergency Stop
(`POST /api/output/stop`), `Server.Close`, a superseding Start and the 5 s
pattern watchdog all terminate the E1.31 stream identically. `handleStopAllOutput`
needed no edit -- it already called `RigCheck.Stop()` -- and that is asserted by
a socket test rather than assumed. Without it, receivers would hold a zeroed
stream until their 2.5 s `E131_NETWORK_DATA_LOSS_TIMEOUT` expired.

reintroducing the latency the revert removed, and it is strictly more robust
than tuning a timing threshold.
