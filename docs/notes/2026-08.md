## 2026-08-04 — Phase 1a: wire-format verification

Root cause of doing this phase at all: the protocol reference doc was compiled by an agent without primary-source cross-checking, and DMX/RDM implementations are notorious for byte-order and offset bugs that silently corrupt data rather than crash. A dedicated research pass (`phase1a-wire-format-verification_2026-08-04_2305.md`) cross-checked the reference doc against primary/independent sources (Art-Net 4 spec PDF, E1.20 spec, OLA's maintained `ArtNetPackets.h`).

**Six corrections found, all fixed before any codec was written:**
1. ArtPollReply has NO ProtVerHi/ProtVerLo — header is ID(8)+OpCode(2)=10 bytes only, not the 12-byte common header other packets use. The reference doc's "common header for all packets" claim was wrong for this packet type.
2. ArtTimeCode has one filler byte, not two — offset 12 is Filler1, offset 13 is StreamId (not Filler2), Frames moves to offset 14, total packet is 19 bytes not 20.
3. **Highest-risk finding:** DUB response encoding is bitwise OR/AND, not XOR as both the reference doc and the original task brief stated. Correct: encode `byte1 = D | 0xAA`, `byte2 = D | 0x55`; decode `D = byte1 & byte2`. Confirmed by mathematical derivation and a real firmware test vector. An XOR implementation would have silently corrupted every discovered UID.
4. ArtPollReply's `EstaMan` field is little-endian while the same-named field in ArtPoll is big-endian (`EstaManHi`/`EstaManLo`), and `ArtPollReply->Oem` is BE in the same packet where `EstaMan` is LE — byte order is not consistent even within one packet. Root cause of flagging this explicitly: a "mostly BE" heuristic would have been wrong often enough to matter.
5. ArtPollReply's `Port` field is little-endian (same as OpCode) — reference doc's endianness callout only mentioned OpCode.
6. ArtPoll's flags byte is officially named `Flags` in the current spec, not `TalkToMe` (an older informal name) — same bit semantics, cosmetic only.

**Left unresolved (flagged, not guessed):** exact byte offset of `BindIndex` in Art-Net 4's `ArtTodData` — the Art-Net 4 changelog says it was added, but the primary PDF fetch was truncated before that section, and OLA's actively-maintained struct has no `bind_index` field at all. Decision: do not hardcode an offset; keep raw `Spare` bytes in the codec and confirm against real EN4 captures in Phase 1d. Also flagged as weakly-confirmed-not-confirmed: ArtRdmSub field endianness (inferred, not explicitly stated in source spec text).

Golden fixtures (hex byte sequences) captured in the report §3 for later use as codec test fixtures.

## 2026-08-09 — Pivot: Windows-primary, Go

**Root cause of the pivot:** Dom re-prioritized — Windows app first, iPhone later. This wasn't a technical failure of the Swift approach; it was a product-priority change. Chosen delivery model: headless server + browser UI. `benny512.exe` runs on one PC on the lighting network; any device's browser (same PC, another laptop, a phone on venue Wi-Fi) opens the UI over LAN. This also **eliminates** the Apple multicast-entitlement risk that Phase 1a's original iOS scope carried, since the phone's browser never touches the network directly — only the server does.

Consequences captured in architecture rev 5 (`rdm-app-architecture_2026-08-09_2236.md`, supersedes `_2246.md` and earlier):
- **Language pivot to Go** (decision #10). Reasoning: agents can cross-compile a single self-contained `benny512.exe` from the Linux sandbox so Dom never installs a toolchain; Go's stdlib covers both UDP networking and HTTP serving in one language. The Swift Phase 1a code becomes the **byte-equivalence reference** the Go port must match, not throwaway work — its cost is preserved.
- Wire-format verification report and golden fixtures carry over unchanged — they were language-independent by design.
- iPhone app is deferred to Phase 6 and may end up as a browser PWA wrapper rather than native, since the browser-UI model already covers phone use.
- Multi-NIC desktops mean interface picker becomes a first-class Settings feature (bind/broadcast interface selection) — this wasn't a concern for a single-radio iPhone.
- **DLux Rackmaster reviewed as design reference** (decision #11). Dom's explicit, deliberate caveat: Rackmaster is not fully tested or finished — inspiration only. Every borrowed idea (MVR/GDTF parsing knowledge, CSV auto-mapping, merge-conflict UX) is re-implemented and independently validated; no Rackmaster code is assumed correct; the Rackmaster folder is never modified.

**Working model established as a standing rule from this point forward:** the architect/orchestrator session does not write code. Dom, verbatim: *"you're far too expensive to be working on small tasks — leave building to the drones."* Implementation, research, and documentation are delegated to subagents — Opus for tricky state machines, Sonnet for codecs/UI/docs. The architect writes briefs, reviews subagent reports, and runs one-command gate checks (`go test -race ./...`) but makes no direct edits. End-of-phase ritual established as mandatory: append to this Project Notes file, and write a fresh timestamped handoff brief, every phase.

## 2026-08-09 — Phase 1b: session engines (Opus-built)

Session/state-machine layer built by an Opus subagent (per the working model: tricky state machines go to Opus): `internal/session/artnetsession.go` (ArtPoll cycle, node table, liveness tracking), `internal/session/rdmcontroller.go` (per-UID serialized transaction queue, transaction-number matching, ACK_TIMER handling as the expected normal path for LumenRadio proxies, ACK_OVERFLOW handling via same-GET repeat with no interleave, configurable timeout profiles for Direct vs Wireless-proxy topologies, NACK decode, multi-block ToD assembly), `internal/session/dmxout.go` (per-universe frame buffer, ~40 Hz output ticker).

Notable judgment calls made and documented in code/tests (not elsewhere) since the spec doesn't fully dictate implementation behavior: transaction-number (TN) policy is retransmit-reuses-TN but ACK_TIMER re-issue and overflow continuations get a fresh TN; overflow hold is tracked per-UID globally rather than per-transaction; broadcast RDM commands complete immediately as `ResultBroadcast` since no device ACKs a broadcast; Table-of-Devices (ToD) entries are keyed by `(IP, PortAddress)` rather than `BindIndex` (a direct consequence of BindIndex being unresolved from Phase 1a's verification pass); ToD completion is judged by counting deduplicated UIDs against `UidTotal`, not by `BlockCount`, since block count alone doesn't guarantee no duplicate UIDs across blocks.

Result: **91 tests**, all using a fake clock (`FakeClock`) rather than real sleeps, scripted against fake transports rather than real sockets. Committed as `9936cba — Phase 1b: session engines — ArtNetSession, RDMController, DMXOutputEngine + state-machine tests`.

## 2026-08-13 → 2026-08-14 — Phase 1c+ : manufacturer PIDs, sensors, device classes, node configuration

**Origin:** Dom, after running the first exe in `--demo`, requested four additions: (1) somewhere to send manufacturer-specific PIDs (his example: Chroma-Q Color Force 48 exposes pixel count, refresh rate, LED flip over RDM); (2) a sensors section per device with a visual gauge/meter indicator; (3) recognition that nodes, splitters and wireless units are themselves RDM-manageable (LumenRadio units report signal quality and name, and allow toggling RDM proxy) — i.e. non-fixture devices are first-class; (4) mid-phase addition: setting IP address / subnet and per-port universe + protocol assignment on nodes and devices "where possible."

**Key architectural insight driving the whole feature set:** RDM is self-describing. `SUPPORTED_PARAMETERS` (0x0050) enumerates what a device supports, and `PARAMETER_DESCRIPTION` (0x0051) returns a manufacturer PID's label, data type, command class, unit, prefix, min/max/default. Therefore Benny512 hardcodes **no vendor tables** — one generic editor renders any device's custom parameters, including gear we have never seen. Same principle for sensors (`SENSOR_DEFINITION`/`SENSOR_VALUE`) and device typing (DEVICE_INFO product category).

### Research pass (agent, Sonnet)
Produced `rdm-pids-sensors-research_2026-08-13_2347.md` — offset tables and complete numeric enum tables (data types, units, prefixes, sensor types, product categories, status types, E1.37-1/-2 PIDs), five golden fixtures with checksum arithmetic, per-item CONFIRMED / WEAKLY CONFIRMED / UNVERIFIED status. Cross-verified against OLA (`RDMEnums.h`, `pids.proto`) and ETCLabs (`defs.h`), plus manufacturer manuals.

Findings that shaped implementation:

- **Chroma-Q Color Force II manual confirms** it implements PARAMETER_DESCRIPTION and SENSOR_DEFINITION/VALUE — validating the generic approach against Dom's actual fixture.
- **LumenRadio Aurora manual confirms** RDM proxy enable is tied to `DMX_PERSONALITY` (not a custom PID), and signal quality is exposed as a **standard sensor**, not a manufacturer PID.
- Manufacturer IDs resolved: Chroma-Q `0x5370`, LumenRadio AB `0x4C55`, Elation `0x22A6`, ETC `0x6574`. Obsidian's own ID unresolved (ADJ `0x1900` vs Elation `0x22A6` both candidates) — demo uses `0x1900`; **confirm on hardware**.
- Product category tree confirmed identical across both independent sources → safe basis for device classification.

**Root-cause bug found and fixed during this work (affects real hardware mode, not just demo):** `web.Server`'s WebSocket pumps were reading directly from `ArtNetSession.Events()` and `RDMController.Events()` — the same channels `Registry.Run()` consumes. ### Patch model, reconcile, rig check (agent, Sonnet) — commit `2aef649`

New `internal/patch` package:
- `entry.go` — the `Entry`/`Patch` model (universe, address, footprint, manufacturer, model, fixture number, confirmed UID). Tolerant JSON persistence to `benny512-patch.json` beside the exe (same directory-of-exe pattern as `internal/walk`'s store), atomic tmp+rename write, migrate-on-load (`migrate()` upgrades any older/missing/zero schema version — currently a no-op beyond stamping `CurrentSchemaVersion`, present so a future field rename doesn't need a data migration story built from scratch).
- `collision.go` — structured collision findings: channel-range overlap between entries, >512 overflow, duplicate fixture numbers, zero/invalid footprints.
- `match.go` — the tiered patch↔RDM matcher, the centerpiece of this phase. Weighted confidence per candidate pair: address 0.40, footprint 0.20, manufacturer 0.15, model 0.25 (`weights` in `match.go`); `proposedThreshold = 0.25` (minimum score to even propose a pairing); `ambiguityMargin = 0.10` (candidates within this margin of the top score are reported as ambiguous rather than auto-resolved). The weights are deliberately tuned so address alone (0.40) usually suffices, but strong corroboration on a *differently*-addressed device (footprint + manufacturer + model = 0.60) can outscore a weak address-only match — that's what catches physically swapped fixtures on a rig (see `TestReconcile_SwappedPair`). Manufacturer/model matching uses **asymmetric token-containment** fuzzy matching (how much of the *reference's* tokens appear in the candidate), deliberately not symmetric Jaccard — a candidate string that's a superset of the reference shouldn't be penalized the way two partially-overlapping strings would be. Matching is **greedy per-entry, not globally-optimal bipartite** — documented in-file as an intentional simplification worth revisiting if real rigs produce bad pairings (a proper assignment-problem solve is more code than the phase warranted). Result rows classify as Matched / AddressMismatch / Missing / Unpatched / Ambiguous, each carrying the evidence (which factors agreed/disagreed and their scores) that drove the classification.
- `rigcheck.go` — channel-level sequencer driving `DMXOutputEngine` to walk the patch fixture-by-fixture, output a settable level, with stop+blackout safety discipline (any transition out of an active rig-check session forces a blackout write before the engine is released — no channel is ever left live because a caller forgot to zero it).

`internal/web/patch.go` adds 25 REST endpoints under `/api/patch/*` (`GET /api/patch`, entry CRUD, reorder, `/collisions`, `/reconcile` + confirm/reject/fix/fix-all, `/adopt`, `/export`, `/reconcile/export`, and eight `/rigcheck/*` control endpoints) plus WS wiring. New Patch screen (`patch.js`, 763 lines post-retheme) with three views: entry table, Reconcile, Rig Check.

**Adopt-discovered-devices-as-patch** (`/api/patch/adopt`) was added as the fastest path to a *working* patch now that CSV is deferred: snapshots the live discovered rig into patch entries with UID pre-confirmed, merge-into-existing that won't clobber entries the user has already hand-edited.

**Bug found and root-caused during this work:** registry fixtures in `--demo` never had their live RDM labels (manufacturer/model) fetched, so reconcile against the demo patch was producing false Ambiguous results — not because the matcher was wrong, but because the demo data feeding it was incomplete. ### Clear discovered RDM devices (agent, Sonnet)

`POST /api/devices/clear`, body `{"scope":"all"}` or `{"scope":"port","ip":"...","portAddress":N}`. Returns `{"scope":...,"cleared":N,"todCleared":N}`; 400 on a malformed body, unknown scope, unparseable IP or out-of-range port address.

Clears the `internal/registry` device entries for the scope **and** the `RDMController`'s Table-of-Devices tables for the affected `(IP, PortAddress)` keys. Clearing the registry alone would have been the subtle bug here: the next Discover merges into the existing ToD rather than replacing it, so a stale ToD would have silently resurrected devices Dom had just cleared, and the feature would have read as "doesn't work" on the bench.

New supporting methods, each in the package that owns the state: `Registry.ClearDevices()` / `ClearDevicesOnPort()`, `RDMController.ClearToD()` / `ClearToDPort()`, `ArtNetSession.ClearNodes()`, `params.ClearAllDeviceState()`, `patch.Store.Clear()`, `capture.Ring.Clear()` (keeps capacity and subscribers, deliberately does not rewind `Seq`). Broadcasts `{"type":"devices_cleared","scope":...,"cleared":N}` over the WS hub so a second browser that didn't initiate the clear still refreshes — verified live across two tabs.

**Async behavior found and characterized while testing (not a bug, but worth knowing at the bench):** `RDMController.HandleTodData` always emits an `EventToDUpdate`, which `Registry.Run()` folds back into the fixture table on its own goroutine. A ToD response that is already in flight when a clear happens will repopulate entries just cleared. This is correct production behavior — a late-arriving Discover result *should* land — but it means a clear issued during an active discovery may appear not to have taken. Clear first, then discover.

### Full reset (agent, Sonnet)

`POST /api/reset`, gated on `{"confirm":"RESET"}` (400 otherwise). Order matters and is deliberate:

1. **Stop the rig check with its existing blackout discipline, and black out DMX output** — before anything else. Never leave the rig lit through a reset.
2. Clear the walk session's identify state.
3. Clear registry devices *and* the Art-Net node table, all ToD tables, the params descriptor cache and per-UID introspection state, and both capture rings.
4. Close the RDM disk logger.
5. Delete `benny512-patch.json` and `benny512-rigwalk.json`, reporting each deleted path and any failure. A missing file is not an error.
6. Reset `Settings` to the same defaults `web.New` installs.
7. Write and flush the 200 **before** exiting, then trigger shutdown on a goroutine after ~500ms so the response actually reaches the browser.

Two structural gaps had to be closed to make this possible. `Server.SetWalkStorePath` / `SetPatchStorePath` **discarded the path** after constructing the store, so nothing on the server knew what file to delete — the paths are now retained. ## 2026-08-25 (later) — Phase 1d first hardware contact: the ArtRdm start-code bug

**Origin:** Dom ran `benny512_082526_1151AM.exe` against real gear and sent `Logs\RDM-LOG.txt` with the observation *"Seems like we're detecting devices on the line, but not resolving their parameters."* This is the first real-hardware evidence the project has ever had, and it immediately found a wire-format bug that eleven commits, 482 tests and a dedicated verification phase had all missed.

### What the log said

- Target: an Obsidian/Elation-family gateway at `2.11.90.4`, Art-Net protocol version 14, 4 ports (BindIndex 1→Address 0, 2→1, 3→2, 4→3).
- **Discovery worked.** ArtTodControl (AtcFlush) → ArtTodData round-tripped on every port, and on Address 0 returned a real fixture: `uidTotal=1`, UID **`22A6:004D05BF`** (Elation Professional, manufacturer 0x22A6). That single fact rules out an enormous amount: the fixture is powered, wired, terminated, RDM-capable, and answering DUB discovery on the physical line. The node's RDM engine is enabled and working.
- **Every directed RDM request was ignored.** 42 `OUT ArtRdm`, **0 `IN ArtRdm`**. Seven different PIDs (DEVICE_INFO, PARAMETER_DESCRIPTION, PRODUCT_DETAIL_ID_LIST, DEVICE_MODEL_DESCRIPTION, MANUFACTURER_LABEL, SOFTWARE_VERSION_LABEL, PROXIED_DEVICE_COUNT), each retried 3× at 1.5 s, then abandoned. No responses. No NACKs. Silence.

Seven different PIDs all failing identically is not a fixture quirk — it is every request being discarded before the fixture ever sees it.

### Root cause

**Benny512 was putting the RDM `0xCC` DMX start code inside the Art-Net `ArtRdm` payload. The spec says it doesn't belong there.**

Art-Net's `RdmPacket` field begins at the RDM **sub-start code** `0x01` (SC_SUB_MESSAGE); the `0xCC` start code is excluded. OLA's Art-Net implementation states it outright in its ArtRdm receive path (`plugins/artnet/ArtNetNode.cpp`), verbatim:

> `// The Art-Net packet does not include the RDM start code. Prepend that.`

and its `artnet_rdm_s` struct ends in a bare `uint8_t data[ARTNET_MAX_RDM_DATA]` with no start-code byte accounted for.

A sample outbound packet from the bench log, byte-verified correct in *every other respect* — valid RDM checksum (0x04AF), message length 0x18, Net=0/Address=0 exactly matching where the device was discovered:

```
4172742d4e6574000083000e010000000000000000000000 cc011822a6004d05bf7ff00000000100010000002000600004af
                                                 ^^ this byte should not be here
```

The gateway parses the payload, finds `0xCC` where the sub-start code must be, and drops the packet without responding. Discovery was unaffected because ArtTodControl/ArtTodData carry no RDM payload at all — which is precisely the discovery-works/GETs-silent split Dom observed.

### Why the verification phase missed it, and why the tests confirmed the bug

`phase1a-wire-format-verification_2026-08-04_2305.md` §2.8 tabulates ArtRdm offsets 0–23 and marks every one CONFIRMED against the Art-Net 3 PDF. **The table has no row for the trailing `RdmPacket` field at all.** That requirement lives in the spec's prose, not in the offset table, so a table-extraction pass had no reason to surface it. The §3.8 golden fixture ("ArtRdm carrying an RDM GET DEVICE_INFO request — 50 bytes total") was then *constructed by the same agent from the same assumption*, so it is not independent confirmation of anything — and every subsequent test asserting that fixture has been faithfully confirming the bug ever since.

**The general lesson, worth carrying into Phase 2b:** a verification pass that extracts offset tables will silently miss requirements stated in prose, and a golden fixture built by the same pass inherits the same blind spot rather than catching it. Where a field's *framing* (as opposed to its offset) matters, check an independent implementation's actual wire behavior, not just the spec table.

### The fix

- **Send side is now spec-correct.** `artnet.Rdm.RdmData` holds the wire payload excluding `0xCC`; `EncodeRdmPacket` strips it. The DEVICE_INFO request drops from 50 bytes to 49.
- **Receive side accepts both framings.** `Rdm.DecodedRDMMessage()` decodes as-is if the payload starts `0xCC`, otherwise prepends it (on a copy — never mutating the caller's slice). Some nodes in the wild do include the start code; a controller that rejected those would have traded one silent failure for another.
- **`--legacy-rdm-startcode`** (default off) restores the old outbound framing, and **the active mode is logged once at startup**, so any captured log self-identifies which framing produced it. This exists because a wrong guess costs a whole bench session; it is a 30-second A/B at the rig rather than a round trip through a new build.
- The flag is threaded as a parameter (`session.RDMConfig.LegacyRdmStartCode`), not package-level global state.
- **ArtRdmSub needed no change** — it is a fully field-based encoding (`ParameterID`, `SubDevice`, `[]uint16 Data`) that carries no embedded RDM PDU and therefore no start code. Confirmed structurally, not assumed.
- Golden fixture corrected to the 49-byte form; the old 50-byte form is retained as `TestGoldenArtRdmEncodeByteExactLegacy` guarding the flag.
- Verified on the wire, not just in tests: a live `--demo` run with `--logrdm` shows `OUT ArtRdm size=49`, payload beginning `01 18 …`, and `IN ArtRdm` decoding cleanly through the tolerant path.

### Second fix — the log could not have answered this question on its own

While diagnosing, a real gap surfaced in the diagnostic instrument itself.

`capture.DecodeEntry` **discarded the decode error entirely** and left `Kind: "unknown"`, which `IsRDMKind` rejects — so the RDM disk log only ever recorded packets that *successfully decoded* as an RDM-family opcode. An inbound packet that arrived but failed to parse never reached the log at all.

That means `RDM-LOG.txt` was structurally incapable of distinguishing **"the gear never answered"** from **"the gear answered and we dropped the packet"** — the exact two hypotheses the log exists to separate, and the two with completely opposite fixes. In this instance it happened not to matter (the requests really were being ignored), but that was luck, and at a bench the cost of that ambiguity is a wasted session.

Fixed:
- `capture.Entry` now carries `DecodeErr`, populated from `artnet.Decode`'s error.
- Undecodable datagrams are routed to the RDM ring and the disk log, **uncapped**, and always with their hex — `HexThreshold` is deliberately bypassed for them, because for an unparseable packet the raw bytes are the only evidence there is.
- Inbound datagrams carrying a **valid Art-Net envelope with an unrecognized OpCode** are logged too. This is a genuinely different state from a decode failure (`artnet.Decode` returns `err == nil` with `Kind == "Unknown"`, capital U, vs. the lowercase `"unknown"` fallback used only on real errors — a case-sensitivity trap now guarded by named constants `KindUnrecognized`/`KindUndecoded`). These *are* capped: 15 per `(peer, opcode)` pair, then a single suppression line naming the pair, with a running count kept. Without the cap a node emitting ArtSync at frame rate would flush the 100k-entry RDM ring and defeat its whole purpose.
- Inbound only — an unrecognized *outbound* opcode would be a bug in this program, not gateway behavior, and doesn't belong in a log meant to diagnose the device.
- Confirmed by reading `transport.UDP.recvLoop` and `Demux.pump` that every inbound datagram surviving the socket read does reach the tap. Pre-existing caveat noted, not a new finding: both the socket's channel send and the demux fan-out drop non-blocking under backpressure, by deliberate "never stall the socket" policy.

### Observation for the bench, not a bug

The log shows Benny512 requesting `PARAMETER_DESCRIPTION` (0x0051) for **standard** PIDs — 0x0011 PROXIED_DEVICE_COUNT and 0x0070 PRODUCT_DETAIL_ID_LIST. PARAMETER_DESCRIPTION is only defined for manufacturer-specific PIDs (0x8000–0xFFDF), so real gear will NACK these with UNKNOWN_PID. That appears to be the deliberate generic-ESTA-PID fallback probing from Phase 1c+, and the demo run confirms the NACK path is handled correctly — but it does cost three round trips per standard PID on real hardware. Worth watching at the bench: if introspection feels slow on a large rig, this is the first place to look.

**The log said the start-code fix worked outright: 240 requests out, 240 responses in.** That is the whole point of that fix, confirmed. What it exposed was the next layer.

**134 of 152 NACKs were `NR_PROXY_BUFFER_FULL` (0x000A).** Split by responder:

| UID | Device | ACK | PROXY_BUFFER_FULL |
|---|---|---|---|
| `4C55:EFAD7AF2` | Moonlite acting as proxy | 78 | 0 |
| `4C55:6DA2C93B` | Moonlite on the far side | 4 | 80 |
| `22A6:004D05BF` | Elation KL Core IP | 1 | 54 |

The only device answering cleanly was the one that *is* the proxy. Everything across the CRMX link was being refused.

Two measurements identified the mechanism: **median 32 ms between outbound requests**, and **median 0.000 s between receiving a PROXY_BUFFER_FULL and hitting that same device again.** E1.20 defines that NACK as "retry later"; Benny512 treated it as terminal.

**But the retry gap was not the whole story, and the deeper cause is the one that produced the user-visible symptom.** `registry.noteParamNack` marks `ManufacturerLabelKnown` / `ModelDescriptionKnown` true on *any* `ResultNack` — the reasonable "asked and answered, stop showing this as pending" rule. So **a single proxy refusal permanently recorded "this device has no manufacturer label."** That is exactly what Dom saw: the KL Core frozen at address and footprint, the far Moonlite showing only a name that Benny512 derived from the `4C55` ESTA-table lookup on its UID prefix rather than anything the device ever said. The devices were not failing to answer — they were being marked as having answered.

**The fix:**

- A distinct `ResultProxyBufferFull` kind, which falls through registry's `ResultNack` switch untouched, so the fixture stays "not yet attempted" and a later backfill retries. This is why a new `ResultKind` was worth it rather than reusing `NackError`: it fixed the cache-poisoning without editing `internal/registry` at all.
- Exponential backoff (250 ms ×2 to a 4 s ceiling, 5 attempts = 7.75 s of patience, inside `ProfileDirect`'s 15 s command deadline), driven through the injected `Clock` so it stays deterministically testable.
- **The pause is keyed on a new `linkKey` of (node IP, bind index, Port-Address), deliberately independent of the configured `SerializationScope`** — because the scope is not the constrained resource. Under `ScopeUID` a per-queue pause would leave other UIDs free to hammer the same CRMX link through their own queues; under `ScopeNode` it would throttle three innocent EN4 ports. The bench evidence settles it: the refusals came from devices *behind* the proxy while the proxy's own UID answered 78/78, so the refusing UID is not even the right thing to pause.
- Pacing is **adaptive, not profile-driven**: a link that returns PROXY_BUFFER_FULL gets a minimum inter-request gap (100 ms, doubling to 2 s), relaxing after sustained success and dropping away below 50 ms. A link that has never refused sees one nil map lookup and is not slowed at all.

**Discovered while doing it: `ProfileWirelessProxy` is dead code.** `SetNodeProfile` is called nowhere outside tests, and neither `main.go` nor `demo.go` sets `RDMConfig.DefaultProfile`, so every production command has always run `ProfileDirect`. The instruction "don't make correct behavior depend on the user picking the right profile" turned out to be stronger than intended — there is currently no way for a user to pick it at all. Flagged, not fixed.

**Two more from the same log:**

`ACK_TIMER` responses were being run through the PID-specific decoder and rendered as nonsense — an ACK_TIMER for `DMX_PERSONALITY` printed *"personality 0 of 30"* when `0x001E` was the timer value, not a personality count. At a bench that reads as a fixture reporting 30 personalities. Fixed at the decision point (`buildRDMDetail` now gates the decoder on `responseType`) rather than per-PID; `NACK_REASON` had the same bug class and is gated too. The **Phase 1a ACK_TIMER unit ambiguity is resolved in the rendered output to 10 ms units** per E1.20, with a comment recording that the observed 313 ms re-issue corroborates rather than proves it. `internal/session`'s own `AckTimerUnit` doc comment still carries the old hedge — follow-up.

**On the 13ch/11ch question — Benny512 was right and the fixture said 13.** The KL Core's DEVICE_INFO came back checksum-valid with `01 00 | 00 4D | 05 09 | 00 00 00 01 | 00 0D | 05 | 09 | 00 01 | 00 00 | 01` — bytes 10–11 are `00 0D` = 13, personality **5 of 9**. The decode was correct; the fixture genuinely reported a 13-slot personality. What was missing was any way for Dom to see *which mode that is*. `DMX_PERSONALITY_DESCRIPTION` (0x00E1) now has a tested standalone codec and a server route — and it turned out `devicedetail.js` was **already calling that endpoint, which 404'd**, masked by `Promise.allSettled`. Device detail now shows `Personality 5/9 — "13ch Extended" (13 slots)`. Only the current personality is fetched on load; the full list is behind an explicit action, since these devices sit behind a bandwidth-constrained proxy.

### Round 3 — Send, Nodes, and the instrument missing its own startup

**Origin:** three bench requests from Dom: live fader scrubbing so he can mix colour and see pan/tilt move; "send channels even at 0 — maybe a per channel toggle"; and on the Nodes tab, every port's input/output showing "n/a" plus IP/networking changes doing nothing.

**Send: the reported symptom was a feature request, the actual finding was a broken fader.** `commit()` built its payload as *only non-zero channels*, and `handleDMX` only wrote channels present in that payload — so **a fader dragged from 200 back down to 0 was omitted from the request entirely and stayed lit at 200 on the rig.** Not "zeros aren't sent"; a fader that cannot go down. Dom chose full-frame output (all 512 slots, zeros included, the way a console does it) plus a per-channel park toggle.

Live scrubbing runs at ~30 Hz, coalesced. The old `pendingSend` guard silently **dropped** a commit when one was already in flight — harmless when committing on blur, but with live scrubbing that would leave the rig on a stale intermediate value at the end of a fast drag. Replaced with a trailing-edge throttle: newest value wins, at most one request in flight, final value always lands. Verified against the engine's actual DMX frame via a throwaway debug endpoint on a scratch copy of the repo, not just the DOM — the DOM agreeing proves nothing about what reached the rig.

Park freezes a channel and ignores drags while still transmitting it. **The UI copy states plainly that this guards against a stray drag — a hazer, a dowser — and does not hand the channel back to a console**, because an Art-Net universe is all-or-nothing while you are outputting and a lighting tech should not have to infer that from a checkbox.

**Nodes: no evidence existed to diagnose from.** Both reported problems live in packet families the disk log never recorded. Added `--lognodes` (requires `--logrdm`): `ArtAddress`/`ArtInput`/`ArtIpProg`/`ArtIpProgReply` logged in full, since they are rare and user-initiated; `ArtPoll`/`ArtPollReply` bounded per peer with an explicit suppression line, since that is continuous background chatter that would otherwise bury the RDM exchanges the file exists for. **ArtPollReply renders `NumPorts`, `NetSwitch`/`SubSwitch` and per port the raw `PortTypes`/`GoodInput`/`GoodOutputA`/`GoodOutputB`/`SwIn`/`SwOut` bytes in hex alongside the decoded reading — never the reading alone**, because the question being asked is precisely whether our decode disagrees with the wire.

**A real bug found while verifying that logging, and it is the same failure class as the two before it.** The disk logger was armed *after* `buildDemo`/`buildReal` had already generated startup traffic, so the seed ArtPollReply and the RDM warmup were handed to a no-op logger and lost. Real mode self-heals on the next poll tick; demo mode never re-polls, so its first ArtPollReply could **never** appear in the log at all. That is the exact packet needed to answer the PortTypes question — quietly missing from the instrument built to capture it. `buildDemo`/`buildReal` now split construction from traffic generation and return a `start` func, so `main()` completes every piece of configuration before a single packet moves. Regression test proved non-tautological by temporarily reinstating the old ordering and confirming a 0-byte log.

On the Nodes screen itself: where a port reports neither `PortTypes` bit, the **raw byte is now shown next to the "n/a"** so it is diagnosable at a bench rather than a dead end. The per-port input-enable control now reads "not confirmed by node" — ArtPollReply has no read-back for it, and a bare unchecked box was presenting a client-side default as confirmed hardware state.

**The flaky harness is fixed rather than characterised for a fourth time.** It failed a full-suite run and had to be manually ruled out twice in one session, which is the documented threshold. `runHTTPAsync` raced a real 3 s wall-clock deadline against a fake clock; it now resolves purely by bounded fake-clock advances plus scheduler yields. **A second, independent race surfaced while proving the first fix:** `RDMController.completeLocked` sends on `cmd.done` *before* emitting `EventCommandComplete`, and `Registry.Run()` applies that event on its own goroutine — so a caller can observe an HTTP result before the registry reflects it, with no clock involved at all. Tests now use a broadcast-sentinel barrier through `Registry.RDMEvents()`. Proven under load: 90 runs under 10-way CPU stress, zero failures.

**That second race is reachable in production, not only from tests, and is deliberately left unfixed pending a decision.** `devices.js`'s `classifyUnknown()` awaits its param calls and then immediately re-fetches `/api/fixtures`, so a freshly-classified device can render one pass stale. Low severity and self-correcting on the next poll, but real. Reordering the two statements in `completeLocked` would **not** actually close it — that only guarantees the event is queued, not that `Registry.Run()` has processed it; the honest fix is for the HTTP handler to wait on registry application, which is a bigger decision than this round warranted.

## 2026-08-25 (late) — Phase 1d, fourth hardware round: the pacing was wrong, and the model behind it was wrong

Round 3's fix shipped, Dom ran it, and the result was worse for the device that had been working. This entry is mostly about reading the evidence honestly enough to revert something built one round earlier, and about what four rounds of logs from the same rig say once they are lined up next to each other.

**Origin:** Dom ran `benny512_082526_0854PM.exe` against the same rig — an Obsidian EN4 at `2.11.90.4`, all three RDM devices on one port (`addresses: [0]`, `uidTotal=3`): `4C55:EFAD7AF2` (a LumenRadio Moonlite acting as the CRMX proxy, on the wired side), `4C55:6DA2C93B` (a Moonlite on the far side of the wireless link) and `22A6:004D05BF` (an Elation KL Core IP, also wireless side). His report: *"now I'm not even seeing all of the info for either moonlite."*

---

### What the pacing actually did

It worked mechanically and did not solve the problem. Median gap between outbound RDM requests went **32 ms → 2.025 s** (p90 4.025 s). PROXY_BUFFER_FULL stayed at **112 of 133 responses**.

That single fact invalidates the model the round-3 fix was built on. **A refusal that survives a two-to-four-second gap is not a rate limit.** Message Count is `0` in every response in every log, decoded from the hex at payload offset 16, so it is also not a proxy holding queued messages we never drain.

Three logs, same rig, same evening, lined up:

| | LOG2 — no pacing, 32 ms | LOG3 — paced, 2.025 s | LOG4 — paced, 2.025 s |
|---|---|---|---|
| requests / responses | 240 / 240 | 75 / 75 | 155 / 133 |
| `4C55:EFAD7AF2` (proxy) | **96 tx, 78 ACK, 0 refused** | not addressed | **10 tx, 8 ACK, 0 refused** |
| `4C55:6DA2C93B` | 89 tx, 4 ACK, 80 refused | 9 tx, 1 ACK, 6 refused | 66 tx, 0 ACK, 60 refused |
| `22A6:004D05BF` | 54 tx, 1 ACK, 54 refused | 65 tx, 0 ACK, 61 refused | 62 tx, 6 ACK, 52 refused |

(Counts are unique transactions — `(dst, TN, PID)` — not raw sends. The brief I was working from quoted raw-send counts for two rows, which is why its request numbers differ slightly from these; the ACK and refusal columns agree exactly.)

**Two conclusions come straight off that table, and the second one is the important one.**

**1. Request rate is not the variable.** Sixty times *more* traffic (LOG2) produced zero refusals from the healthy responder. Sixty times *less* traffic (LOG3, LOG4) produced no improvement at all for the sick ones — LOG3 refused 61 of 65 to the KL Core at a 2 s cadence, which is exactly the rate the pacing was supposed to fix things at. Two independent paced runs and one unpaced run agree: pacing does not move the refusal rate.

**2. The refusal is attributable to the target UID, not to the shared link.** Across all three logs the proxy's own UID returned PROXY_BUFFER_FULL **zero times, ever** — 96 transactions at 32 ms in LOG2, in the same seconds that the two devices behind it were being refused 134 times through the same buffer. A genuinely full shared buffer has no room for the *next* response either, whoever it is addressed to. It always had room for `EFAD7AF2`.

Round 3's own reasoning for choosing link granularity was recorded in the last entry: *"under `ScopeUID` a per-queue pause would leave other UIDs free to hammer the same CRMX link through their own queues."* That is a sound argument about a shared buffer, and the data says the buffer being reported full is not shared. The cost of getting it wrong is in the table: the proxy answering 78 of 78 dropped to 10 transactions because two of its neighbours were sick.

### What was removed

**Per-link pacing is gone entirely** — `linkState`, the five `ProxyPace*` constants, `paceWaitLocked`, `stampLinkSendLocked`, `armLinkTimerLocked`, `onLinkPaceElapsed`, `noteLinkTransactionLocked`, and the `links` map on the controller. `linkKey` survives only as half of the new `deviceKey`, so the same UID reached through two node ports keeps independent health rather than one path's failure hiding the other's success.

Reverting one round's work on the next round's evidence is the right outcome, not a failure. The mechanism was correctly built, thoroughly commented and well tested; it was aimed at a cause that does not exist.

**Per-command backoff was cut from five re-issues to two** (250 ms + 500 ms, down from 250 ms → 4 s). It still covers the case E1.20 actually describes — one momentarily-full slot that clears on the next ask — but the persistent case is no longer its job.

### What replaced it: a per-device circuit breaker

Keyed on `(node port, responder UID)`. Three states, and the state a directly-wired device lives in costs one absent-key map lookup per command — no timer, no allocation, no delay, no map entry at all.

- **Closed.** Normal.
- **Open.** After `ProxyBreakerTrip` (3) *consecutive commands* each fail with `ResultProxyBufferFull` — each having already spent its own backoff — the controller stops sending to that device. Commands complete immediately as a new `ResultDeviceUnreachable`, with no wire traffic and no time spent. Cool-down starts at 15 s and doubles per re-open to a 2-minute ceiling.
- **Half-open.** After the cool-down, exactly one probe is admitted. An answer closes the breaker and resets the cool-down; a refusal reopens it for longer.

Budget arithmetic, which is the whole point: a device that refuses everything used to cost roughly 8 s per PID forever — across ~15 PIDs and 3 devices that is the minutes of dead air LOG4 is full of. It now costs three commands (~2.5 s) once, then nothing until a probe.

**Any answer closes the breaker, including a NACK.** "I don't support that PID" came back through the proxy, which is precisely the property being measured.

**A response timeout deliberately does not trip it and does not reset it.** That is not an oversight and it matters — see the next section.

### The silence: Dom power-cycled the EN4

**Resolved. It was a node reboot, mid-capture, and it has nothing to do with Benny512.** Dom confirmed it after this analysis was written. The record of how it was reached is worth keeping, because the evidence pointed away from our code being at fault *before* the answer arrived, and it was right to.

This was flagged to me as the most alarming finding in the round and as unexplained. Reading the log settled two of the three claims about it in the negative.

**It is one contiguous 36-second window in the first minute, not a tail.** From `TN=13` at 21:16:28.897 through `TN=20`'s second send at 21:17:05.408, eight transactions drew no response — 21 retransmissions plus one extra send, which accounts for the 155/133 deficit *exactly*. Every single request after 21:17:05 is answered, all the way to the end of the log at 21:21:26. Nothing else in LOG4 is missing a response.

**The proxy had not "been answering fine seconds earlier."** `TN=17` is the *first* request `4C55:EFAD7AF2` receives in the entire session, and it falls inside the silent window. Its first answer is `TN=44`, after the silence ends. The claim that a known-healthy responder went quiet mid-conversation is not what the log shows — but the weaker version still holds, and still matters: a wired device on the near side of the CRMX link got nothing, so **this was not a wireless-link event.** It was the node, or the wired DMX line.

**It is almost certainly not caused by our traffic.** LOG2 hammered the same node at a 32 ms median for 143 seconds and got 240 of 240 answered with no silence at all. LOG3 ran the identical 2.025 s paced cadence for 2.5 minutes and got 75 of 75 with no silence. LOG4's traffic was gentler than LOG2's in every respect. A retry storm that wedges an EN4 should show up worst in the most aggressive log; it shows up only in the mildest one. **The "our retry storm wedged the node's RDM engine" hypothesis is refuted by our own evidence.**

**What I could not establish from the log was *why*, and I said so rather than picking a story.** Recovery coincides with an `ArtTodControl` AtcFlush at 21:17:04.253 — ArtTodData back 300 ms later, all three UIDs, `uidTotal=3` unchanged — with the first successful RDM response 1.2 s after that. Suggestive of the flush unwedging the node, but **N = 1**: LOG4 contains four flushes and only one correlates with anything. A node-side background discovery pass fit equally well. I declined to choose.

**The answer is that Dom power-cycled the EN4 mid-capture.** The signature fits exactly: a 36-second dead window at every UID simultaneously, ending with a rediscovery that returns the full ToD in 300 ms. Not a wedge, not a discovery cycle, not our retry storm — a reboot. The AtcFlush correlation was real but backwards: the node came back and the flush found it, rather than the flush fixing anything.

**The part worth carrying forward is the negative result, which held up.** Three logs off one rig said our traffic was not the cause before anyone knew what was: LOG2 hammered the node at a 32 ms median and got 240/240; LOG3 ran the identical 2.025 s paced cadence and got 75/75; only LOG4, the mildest of the three, went silent. Any hypothesis that blames our request pattern has to explain why the most aggressive log is the clean one. That reasoning cleared our code correctly, and it is the reason no time was spent "fixing" a retry storm that was never happening.

**And it retroactively validates the breaker's most counter-intuitive design decision.** Timeouts neither trip the circuit breaker nor reset it — written at the time as a defensive guess about an unexplained event. It turns out to be exactly right for a real one: **had the breaker counted silence, a 36-second power cycle would have blacklisted the entire rig**, the healthy wired proxy included, and then held every device out through a 15-second cool-down after the node was already back and answering. A tech who reboots a node to fix something would have watched the tool go blind for the reboot *and* the cool-down, and concluded the reboot made it worse. PROXY_BUFFER_FULL is a statement a device made about itself; silence is a statement about nothing.

### A standing lesson: the bench log is a shared artifact, and hands at the rig are invisible in it

This cost a round-trip and most of an analysis. **Physical actions at the rig — a power cycle, a re-patch, unplugging a run, a radio re-pair — leave no trace in the RDM log, and their signature in the packet stream is indistinguishable from a software fault.** A 36-second silence across every UID reads as "the controller wedged the node" right up until someone says "I rebooted it."

Two cheap fixes, in increasing order of usefulness:

1. **Dom notes the wall-clock time when he does something physical** and sends it with the log. Zero engineering, works today, and would have collapsed this whole analysis into one line. Worth adding to `HARDWARE-TEST-CHECKLIST` as a standing capture instruction, not just for this round.
2. **A "Mark log" control in the UI** that writes a timestamped, user-typed annotation into the disk log. **`capture.NoteEntry`/`DirNote`, built this round for the circuit breaker's give-up lines, is the natural seam** — it already renders a `[timestamp] NOTE …` line with no `peer=`/`size=`, already flows through `Server.logNote` into both the RDM ring and the disk logger, and needs no new entry shape. What is missing is roughly a `POST /api/log/note` handler, a text field and button somewhere unobtrusive (the Analyzer screen is the obvious home), and a prefix distinguishing an operator annotation from a controller decision so the two never get confused when reading back.

**Not built this round** — it is scope Dom has not been asked about, and the checklist change gets most of the value for none of the cost. Proposed as a scoped follow-up.

### The wasted PARAMETER_DESCRIPTION transactions were not fixed

They were fixed in one place and left in another, which is why they were still on the wire two rounds after being identified.

`Introspect`'s walk has been gated on `isIntrospectionTarget` since the waste was first found. **`DescribeParam` → `resolveDescriptor` was not** — and that is the path the generic parameter editor uses (`GET/SET /api/devices/{uid}/params/{pid}`), independently of the walk. It sent PARAMETER_DESCRIPTION for any PID it was handed.

LOG4 caught it against real gear: `0x0070` (PRODUCT_DETAIL_ID_LIST), `0x0080` (DEVICE_MODEL_DESCRIPTION) and `0x0081` (MANUFACTURER_LABEL) — all three standard, all three already in `knownDecodedESTAPIDs`. `TN=115`, the one that reached the healthy proxy rather than a saturated device, came back **NACK 0x0006 (DATA_OUT_OF_RANGE)** — the hardware itself confirming the round trip was pure waste.

(One entry in the log is *not* waste: PARAMETER_DESCRIPTION for `0x0011` PROXIED_DEVICE_COUNT is deliberate, documented in `knownDecodedESTAPIDs`' comment — the UI dropped its dedicated proxy-status callout, so the generic editor is the only remaining way to inspect that PID. That one stays.)

Same gate, now applied at both call sites. The returned descriptor is byte-for-byte what the NACK already produced, so nothing downstream changes shape — the editor still falls back to raw hex for these PIDs. The only difference is that no request is sent. The test was proven non-tautological by reinstating the old behaviour and confirming it fails, naming PIDs `[112 128 129]` — `0x0070`, `0x0080`, `0x0081`, precisely what the bench log shows.

### Making it visible, because a row that stops filling in reads as our fault

Dom's report was about missing information, not about protocol behaviour. Round 3's build made a device disappear from view with nothing on screen to say why — at a bench that is indistinguishable from Benny512 being broken.

- **`registry.Fixture`** gained `ProxyUnreachable`, `ProxyUnreachableSince`, `ProxyRetryAt`, `ProxyRefusals`. Raw facts only; the sentence is composed in the web layer, the same division of labour as `ManufacturerLabel` and `effectiveManufacturer`. `ResultDeviceUnreachable` is routed **away** from `noteParamNack` — recording an unasked PID as "asked and answered" would be the round-2 cache-poisoning bug reappearing in a new place, and there is a test that says so.
- **`fixtureJSON`** gained `unreachable`, `unreachableNote`, `retryAt`. The note is a finished sentence rendered verbatim so the wording is identical in the Devices table, device detail and Rig Walk:

  > **Not answering through its wireless proxy. Benny512 has paused it so the rest of the rig keeps running, and will try again automatically.**

  Wording rules, asserted in a test rather than left to drift: name the thing a tech can act on (the radio link), never the protocol condition — no "NACK", no "PROXY_BUFFER_FULL", no "circuit breaker"; say Benny512 paused it and will retry, so a missing row is never mistaken for a crash or a dropped fixture. The Devices row also carries a **"Not answering"** text tag beside the class tag and a warning-ramp tint. Both signals are text; the tint is decoration on top of them, per the standing never-color-alone constraint. Warning ramp, not the error red, which stays reserved for error/destructive — a fixture we intend to retry is not an error. Render-proved in Chromium: zero `pageerror`, note visible at `rgb(217,154,43)`, row tint applied.
- **The RDM log gained NOTE lines.** This closes a gap the log itself exposed: when Benny512 stops asking a device it stops *sending*, so the decision that explains a suddenly-quiet stretch of log leaves no trace in the log. Reading LOG4 meant inferring "the controller gave up here" from an absence — exactly the inference an instrument should not require. `capture.NoteEntry` + `DirNote` render as a single `[timestamp] NOTE …` line with no `peer=`/`size=`, deduplicated on the breaker's `RetryAt` so one open produces one line rather than one per suppressed command. The recovery gets a line too.
- **`RDMStats.DevicesUnreachable`** counts breaker openings for the diagnostics screen, and **`RDMController.Reachability()`** reports every device that has had trouble this session, whether or not it is currently open.

## 2026-08-26 — Round 5: a hard-line control run, and the PARAMETER_DESCRIPTION gate was still wrong

RDM-LOG6 is a clean hard-line capture against an Elation KL Core IP (`22A6:004D09D1`) — no CRMX, no proxy, direct wire. **82 requests, 82 responses, zero timeouts, zero `PROXY_BUFFER_FULL`.** That headline result matters on its own before anything else in this entry: it isolates the CRMX-link proxy-refusal problem the last several rounds have been chasing away from Benny512's own RDM handling and away from this fixture — on a clean line, this device answers everything, and nothing here times out or gets refused. Whatever is producing `NR_PROXY_BUFFER_FULL` on the wireless run is downstream of the CRMX link, not upstream of it.

**One caveat on that headline, stated plainly so it isn't overclaimed:** this KL Core IP is a *different physical unit* from the one in earlier logs — `22A6:004D09D1` here versus `22A6:004D05BF` in LOG4, both wireless-side. This is a control run on the same model, not an A/B of the same fixture across hard-line and wireless. It proves this unit is healthy directly wired and that our RDM handling produces no refusals against it; it does not, by itself, prove `004D05BF` behaves identically, and it doesn't touch the CRMX link at all — there wasn't one in the path.

Inside that clean run, though, there was real waste, and it is the same bug class as two rounds ago wearing a different shape.

### 25 of 82 requests were guaranteed to fail before they were sent

Every `PARAMETER_DESCRIPTION` (`0x0051`) request in the log — all 25 of them — targeted a standard PID and got NACKed `UNKNOWN_PID`:

```
0x0011 0x0400 0x0015 0x0032 0x0401 0x0402 0x0403 0x0404 0x0405 0x0600
0x0601 0x0602 0x0500 0x0501 0x0603 0x1010 0x1031 0x0122 0x00B0 0x00A0
0x00C2 0x00C1 0x1001 0x0090 0x0000
```

Zero manufacturer-range targets. E1.20 §10.4.2 defines `PARAMETER_DESCRIPTION` only for manufacturer-specific PIDs (`0x8000`-`0xFFDF`); asking a conforming device to describe a standard PID is out of spec, and the log is 25/25 proof a real, healthy responder treats it that way. The device's own `SUPPORTED_PARAMETERS` response (`TN=26`) explains why there was so much to walk: it lists **35 entries, and every one of them is a standard PID** — no manufacturer PID anywhere. E1.20 makes `PARAMETER_DESCRIPTION` itself mandatory *only if* the device implements any manufacturer-specific PID (already documented in this codebase's own `supportedparams.go`), and this device implements none — so it was never going to answer `0x0051` for anything, and indeed `0x0051` is absent from its own `SUPPORTED_PARAMETERS` list too. Three independent signals (the NACKs, the all-standard supported-parameters list, and the PID's own absence from that list) all say the same thing.

### Two different features hit the same wrong gate — not just Introspect

Tracing `TN=2` (the very first `PARAMETER_DESCRIPTION` request in the log, for `0x0011` PROXIED_DEVICE_COUNT) showed it happens *before* `SUPPORTED_PARAMETERS` is even fetched (`TN=26`), which means it can't be `Introspect`'s walk. It's `internal/web/static/js/devices.js`'s `classifyUnknown()` — the Devices *list* screen's background classification probe, which fires from `refreshFixtures()` for every fixture the registry hasn't classified yet (`f.class === 'Unknown'`), independent of anyone opening a device's detail panel. It fetches `device_info`, `0070`, `0011`, `0081`, `0080` by `GetParam`, and `GetParam` calls `DescribeParam` first to know how to decode the response — the same `resolveDescriptor` chokepoint, reached from a third caller `grep` alone wouldn't separate from `Introspect`'s. `0070`/`0081`/`0080` are all in `knownDecodedESTAPIDs` so they were already safe; `0011` is the one PID deliberately left *out* of that list (so the generic editor can still reach it), which is exactly why it was the one that leaked here too.

This matters for the wireless-impact question below: **`classifyUnknown()` is not user-gated.** It runs automatically for every newly-discovered, not-yet-classified device the Devices list renders — once per device per session, before anyone opens that device's detail panel or clicks Introspect. The remaining 24 requests in the log (`0x0400` through the trailing `0x0000`) are `Introspect`'s walk, which *is* user-triggered from device detail (confirmed: `handleIntrospectDevice` is `Client.Introspect`'s only Go caller) — `0x0011` doesn't reappear in that batch because the earlier NACK is already sitting in `descCache`, keyed on `(manufacturerID, pid)`, by the time the walk reaches it.

### Why the round-4 fix didn't catch this

It isn't that the fix from two rounds ago was undone or bypassed. Commit `66c9e58` gated `DescribeParam → resolveDescriptor` on exactly the same predicate `Introspect`'s walk already used (`isIntrospectionTarget`) — architecturally the right move, and it closed the specific gap LOG4 found (`0x0070`/`0x0080`/`0x0081` leaking through the on-demand editor path). **Both call sites were already funneling through one shared gate. The gate's definition was wrong**, and gating two call sites on one wrong rule reproduces the same bug at both of them, which is exactly what LOG6 shows — the walk is the only path that runs unattended (the on-demand path only fires when a UI editor cell is opened), so this round's evidence all comes from `Introspect`, but `resolveDescriptor` would have made the identical mistake if asked.

The wrong part, read straight from the old doc comment: `isIntrospectionTarget` returned true for "any manufacturer PID, **or any ESTA-range PID this package doesn't already natively decode**" — and the comment justified the second half by claiming report §2.2 held that a responder is "technically allowed" to describe standard PIDs, so probing "unknown ESTA PIDs" the same way as manufacturer PIDs was framed as a *feature* (§1.1 item 5's recommendation), not a bug. That claim is simply wrong per E1.20, and RDM-LOG6 is now direct hardware evidence against it: 25/25, no exceptions. The round-4 fix excluded exactly the standard PIDs already in a small hardcoded "we decode this" list (`knownDecodedESTAPIDs`) and left every *other* standard PID — anything the device happened to list that this package doesn't have a dedicated field for — free to be probed. This KL Core's `SUPPORTED_PARAMETERS` is almost entirely PIDs outside that hardcoded list, so almost the whole walk leaked.

### The fix: split one wrong predicate into two correct ones

`isIntrospectionTarget` conflated two different questions that happen to often agree but don't always:

1. **Does this PID get a row in the generic parameter editor at all?** — broad, cosmetic, no wire cost by itself.
2. **May `PARAMETER_DESCRIPTION` actually be sent for this PID?** — narrow, spec-mandated, has a real transaction cost.

`internal/params/introspect.go` now has two functions instead of one:

- **`isDescribable(pid)`** — `pid.IsManufacturerSpecific()`, full stop. This is the *only* thing allowed to authorize a live `GET PARAMETER_DESCRIPTION`, and `resolveDescriptor` is the single chokepoint that consults it — every caller of `PARAMETER_DESCRIPTION` (the walk, the on-demand editor path, and any future one) still has to go through `resolveDescriptor`, so there's no second place left to get this wrong. `Introspect` and `DescribeParam` were already both routed through it before this round; that part of the round-4 architecture was correct and didn't need to change.
- **`isEditorTarget(pid)`** — the old broad rule (manufacturer, or standard-and-not-already-decoded), now used only to decide whether a PID gets an editor row. A standard PID like `PROXIED_DEVICE_COUNT` still gets one — task item 2 from an earlier round ("keep it reachable via the generic editor") still holds — it just resolves straight to a non-self-describing descriptor with zero wire traffic, since `isDescribable` says no before `resolveDescriptor` ever builds the request.

Net effect on this device: `isEditorTarget` still lets all 25 standard PIDs onto the editor's row list (matching the log's evidence that they're all reachable/described-as-raw-hex), but `isDescribable` now stops every one of them from ever reaching the wire as a `PARAMETER_DESCRIPTION` request. Re-run against the fixed code (fake-clock test, `TestIntrospectDoesNotProbeUndecodedStandardPIDs`, reproduces this exact device's `SUPPORTED_PARAMETERS` shape): 0 `PARAMETER_DESCRIPTION` requests, 25 descriptors, all correctly non-self-describing. Confirmed non-tautological by reverting `isDescribable` to the old broad rule and watching the test fail, naming PID `0x0011` as the first illegal probe.

**`TestIntrospectReachesProxiedDevicePIDs`** (the round-4 test guarding the PROXIED_DEVICE_COUNT editor-reachability requirement) previously only checked the *shape* of the outcome — a non-self-describing descriptor is what a NACK would have produced anyway, so a test that only checks the descriptor can't tell "we didn't ask" from "we asked and got told no." It's now instrumented to assert zero `PARAMETER_DESCRIPTION` traffic directly, the same way `TestDescribeParamDoesNotProbeStandardPIDs` already did for the round-4 fix.

### The 0x0000 entry, and a second, smaller waste it caused

The device's own `SUPPORTED_PARAMETERS` response has a spurious trailing `0x0000` — visible straight in the wire bytes (`PDL=70` = 35 two-byte entries, the last one `0000`), not something Benny512 sent. `0x0000` is not a valid RDM PID at all; real PID numbers start at `0x0001`. Before this fix it flowed all the way through: `Introspect` treated it as an editor target, produced a descriptor for it, and the UI's normal "fetch each descriptor's current value" step then issued a live `GET` for PID `0x0000` itself (`TN=75` in the log) — NACKed `UNKNOWN_PID`, same as the `PARAMETER_DESCRIPTION` probe for it a few transactions earlier. So the `0x0000` entry cost **two** wasted transactions, not one: the description probe (already counted in the 25 above) and this follow-on value `GET`.

Fixed at the boundary in `Introspect` where the device's raw, untrusted PID list becomes Benny512's own target list — `pid == 0` is dropped before it can become an editor row, a description probe, or a `GET` of any kind. **Deliberately not fixed inside `rdm.DecodeSupportedParameters` itself** — that decoder is shared with `internal/capture/rdmdetail.go`'s diagnostic capture-log rendering, which is precisely what turned this firmware quirk into a visible, readable `0x0000(Unknown)` line in RDM-LOG6 in the first place. Filtering it out of the shared decoder would launder that evidence out of future bench logs' decoded view (the raw hex is always shown regardless, so nothing would be *lost*, but it would take manual hex-decoding to notice next time). The decoder stays a faithful decode of what the device actually said; the filtering belongs at the narrower point where a decoded list turns into outgoing traffic.

### Should a device that NACKs PARAMETER_DESCRIPTION once be asked again?

Checked the precedent the brief pointed at: `SelfDescribing:false` plus the existing `descCache` (keyed on `manufacturerID, pid`) already stops Benny512 from re-asking about the *same* PID twice. It's being consulted correctly on this path — that much was fine. What it can't do is generalize "this device doesn't implement `0x0051` at all" across *different* PIDs, because it's keyed per-PID. For this specific device that gap is moot: it has zero manufacturer PIDs, so the `isDescribable` fix alone already takes it to 0 `PARAMETER_DESCRIPTION` requests. But a device with several manufacturer PIDs and no `PARAMETER_DESCRIPTION` support (E1.20-legal — it's only mandatory if manufacturer PIDs are implemented, and plenty of real gear under-implements even things it's supposed to have) would still pay one wasted NACK per distinct PID before ever benefiting from the per-PID cache.

Added a second, narrower cache: `uidState.paramDescUnsupported`, set the first time a `GET PARAMETER_DESCRIPTION` NACKs specifically with `UNKNOWN_PID` — E1.20's "I do not implement this command" signal, as opposed to some other NACK reason (`DATA_OUT_OF_RANGE` is the one RDM-LOG4 actually saw a real device use) that might mean "I support the command but reject this particular target." Once set, `resolveDescriptor` short-circuits every later manufacturer-PID probe for that UID without spending a transaction. Two tests pin the boundary exactly: one manufacturer PID's `UNKNOWN_PID` NACK suppresses the probe for a second, different manufacturer PID (`TestResolveDescriptorGivesUpAfterUnknownPIDOnDescriptionItself`); a `DATA_OUT_OF_RANGE` NACK does not (`TestResolveDescriptorDoesNotGiveUpOnOtherNackReasons`), so a responder that's merely picky about one PID doesn't get its other manufacturer PIDs written off.

The brief's arithmetic is right and worth restating precisely: 25 guaranteed-fail transactions at the ~2 s-per-transaction pacing the CRMX link is currently running under is on the order of 50 seconds of dead air per device, and — more importantly given the open circuit-breaker/pacing work from prior rounds — 25 more chances for a wireless-side device to answer into a full proxy buffer while the queue is backed up on nothing. ### Bug 2: "kicked out after a character or two" was a scoping bug wearing a focus-bug's symptoms, and it's fixed

The owner's report matches this project's own history closely — the Phase 1c+ notes already record building the node-config editor once per node selection specifically so live ArtPollReply refreshes couldn't destroy in-progress typing. `devicedetail.js` had the equivalent problem for a different reason: `notify()` took no argument, so *any* async cache update — a background sensor reading arriving over WS, an unrelated info fetch resolving, a params `Apply` completing — called every subscriber, and every subscriber's response to "something changed" was to blindly rebuild whatever section is currently visible, whether or not that section had anything to do with what changed. The periodic sensor push (`sensor_values`, ~2 s interval, keeps arriving for any device whose Sensors accordion/tab has *ever* been opened this selection — there's no auto-unsubscribe on tab switch) is exactly the kind of update that fires on a timer regardless of what the tech is doing, which is why it reliably won the race against typing: type a character or two into Device Label, a sensor push lands, the whole Parameters section — Device Label input included — gets torn down and rebuilt from the last-fetched (pre-edit) value.

The fix, already substantially built by the time this round started: `notify(scope)` now names which section actually changed (`'info' | 'params' | 'sensors' | 'status'`), and both consumers — `devices.js`'s single active-tab view and `walk.js`'s multi-accordion view — check that scope against what's currently on screen before touching any DOM. A `'sensors'` push while Parameters is the active tab now **never calls `renderTabBody` at all** — not "renders it safely," doesn't run. That is the actual fix, not a mitigation: the section that owns Device Label is now structurally unreachable from a sensor push, so there is no re-render for a stray keystroke to lose to. `UI.buildApplyField` also grew an optional `opts.name` that stamps `data-b5-field`, and `devicedetail.js` added `captureFieldFocus`/`restoreFieldFocus` (value + caret, keyed off that attribute) around the *legitimate* same-section rebuilds that remain — an Apply elsewhere in Parameters, an introspect progressing for the currently-selected device — which is the right use of a focus-restore mechanism per the brief's framing: not a bandage over a re-render that shouldn't happen, but genuine preservation across one that must.

## 2026-08-26 (evening) — Cold start proves the proxy buffer is ours to fill, and the ACK_TIMER leak is closed

RDM-LOG8 is the test the last round asked for: the owner power-cycled the MoonLite2 pair and started a session immediately. It settles the question the previous four rounds were circling, and it settles it against us.

**The first request of the session — `TN=0`, `GET DEVICE_INFO` to `22A6:004D09D1` — came back `ACK_TIMER`, not `PROXY_BUFFER_FULL`.** On a freshly powered radio the proxy accepts work normally. Everything after that is Benny512 filling the buffer:

```
TN=0  ACK_TIMER raw=3      TN=14 ACK_TIMER raw=6
TN=1  ACK_TIMER raw=6      TN=15 ACK_TIMER raw=9
TN=2  ACK                  TN=16 ACK_TIMER raw=12
TN=3  ACK_TIMER raw=2      TN=17 ACK_TIMER raw=15
TN=4  ACK_TIMER raw=2      TN=18 ACK_TIMER raw=18
TN=5  ACK_TIMER raw=3      TN=19 ACK_TIMER raw=21
TN=6  ACK                  TN=20 ACK_TIMER raw=24
  …                        TN=21 ACK_TIMER raw=30
                           TN=22 NACK PROXY_BUFFER_FULL
```

Twenty deferrals, four answers, then refusal — on a link with nothing else on it. Totals for the session: `22A6:004D09D1` gave 4 ACKs, 20 ACK_TIMERs and 15 `PROXY_BUFFER_FULL`; `4C55:6DA2C93B` gave 9 refusals; the wired proxy `4C55:EFAD7AF2` answered 19 ACKs throughout, untroubled, as it has in every log.

Two things follow, and the second is the one that mattered.

**The buffer is persistent state across controller sessions.** RDM-LOG7's very first request was refused at `TN=0`; LOG8's was accepted. The only difference is the power cycle. Nothing Benny512 did between those sessions cleared it, and nothing it *could* do had ever cleared it — which is why five bench logs across three days all looked like a dead link.

**The responder's own time estimate climbs monotonically as its queue grows.** 6, 9, 12, 15, 18, 21, 24, 30 across consecutive deferrals of one command, then the refusal. That is the proxy telling us the queue depth in real time while we fill it, and it is as clear a confirmation of the mechanism as a capture is ever going to give.

### The mechanism, and the fix

Benny512 collected each deferred answer by re-issuing the original request under a fresh transaction number. To a proxy that is a *new* transaction: a new buffer slot, a new trip over the air, and the previously parked answer stranded with its slot never freed. Twenty of those exhausts the buffer.

E1.20's actual continuation after `ACK_TIMER` is to wait the estimated time and then collect the parked answer with `GET QUEUED_MESSAGE`, which the proxy serves from the buffer it already holds — freeing a slot instead of consuming one. That is now what the controller does (`internal/session/rdmacktimer.go`). The observable change, from the test that walks this log's shape: eight deferrals of one command used to produce nine requests for the parameter and now produce one, plus eight collections.

This is the `TODO(bench)` left deliberately unimplemented last round, when the evidence for it was still circumstantial. It isn't any more.

### The ACK_TIMER unit ambiguity is settled — and we were already right

`RDMConfig.AckTimerUnit` has carried a "SPEC AMBIGUITY, flagged for architect review" comment since Phase 1c: E1.20 says 10 ms increments, the project's protocol reference described the field as a plain millisecond count, and the difference is a 10× error in retry pacing on exactly the rig where it matters most. LOG8 measures it directly. Inter-response gaps across the twenty deferrals track `raw × 10 ms` plus a 12–30 ms round trip almost exactly:

```
raw=6  → 88 ms      raw=15 → 171 ms
raw=9  → 116 ms     raw=18 → 200 ms
raw=12 → 144 ms     raw=30 → 312 ms
```

A 1 ms unit would make every gap a flat ~30 ms; a 100 ms unit would make `raw=30` over three seconds. E1.20's 10 ms is correct and Benny512 was already honouring it. **This should come off the open-questions list** — it had been flagged to the owner as possibly 10× wrong, and it isn't. The knob stays as an escape hatch for a responder that disagrees, and the test that guards it now records the measurement rather than the ambiguity.

### Why the continuation is tried first but not unconditionally

LOG8 also contains the first field trial of last round's recovery drain, and it is a negative result worth keeping on the record: **six `GET QUEUED_MESSAGE` requests went out across two drain passes, addressed to the two proxied UIDs, and drew zero responses.** Not a NACK — silence, three response timeouts per pass. Separately, `22A6:004D09D1`'s own `SUPPORTED_PARAMETERS` from RDM-LOG6 (taken while it was wired directly, no radio in the path) lists neither `0x0020 QUEUED_MESSAGE` nor `0x0030 STATUS_MESSAGES`.

So on this rig, replacing the re-issue with a bare `QUEUED_MESSAGE` would have traded a path that demonstrably produces answers — four of them in LOG8 — for one that has so far produced none. Unconditional would not have been "correct", merely unconditional.

The shape actually shipped: try the spec path, remember what happened, per device.

- A responder that serves a queued message is collected from for the rest of the session.
- One that answers `UNKNOWN_PID` / `UNSUPPORTED_COMMAND_CLASS`, or stays silent, is marked and never probed again — **one probe per device, not one per deferral.** Silence gets no retransmission budget, so the cost of learning is a single timeout.
- After that fallback, behaviour is byte-for-byte what it was before this round.

`ReissueOnly` remains available as a config escape hatch, and has a test pinning what it costs.

### Routing: what a collected message is allowed to answer

A queued message arrives with no reference to the request it answers. The transaction number on the wire belongs to the `QUEUED_MESSAGE` probe, not to the original request, and E1.20 gives a responder no way to say "this is the answer to the DEVICE_INFO you asked for at 11:46:55". All there is to go on is the PID it was delivered under.

The rule adopted is deliberately narrow: **a collected message satisfies the waiting command only when node, responder UID and delivered PID all agree with what that command asked for, and it is only ever offered to the one command that issued the probe** — never searched for across the whole in-flight set. Anything else is an orphan: a stale answer from an earlier session, or one whose command has already given up. Orphans are published on a new `EventQueuedMessageCollected` and filed by the registry under their own PID, so they are neither attributed nor discarded. Collection then continues, since ours may be further down the queue; a per-command cap (default 4) counts orphans collected, not probes issued, so a responder that is merely still working is not mistaken for one that is stuck.

Two guards were explicitly held unchanged and have tests saying so:

- **Anti-misattribution.** Deciding which *command* a *response* belongs to is still transaction number plus source UID plus command class. A probe changes none of that. A response carrying the wrong UID is still counted stray, even though its PID would have been licensed to float.
- **ACK_OVERFLOW reassembly.** A parked answer can itself span packets. The first block pins the PID and every later block is matched against it as strictly as ever; a block that changes PID mid-sequence still aborts with `ErrOverflowPIDMismatch`.

### The wired path is untouched, and that is tested rather than asserted

RDM-LOG6's hard-line walk is 82 requests, 82 responses, and contains no `ACK_TIMER` at all. A responder that never defers never sees a probe and never gets an entry in the health map — the wired path costs one absent-key lookup per command, exactly as before. There is a test that runs twelve wired commands and asserts zero probes, zero collect/reissue counters and an empty reachability map.

### The recovery drain is now a backstop, and defers to what the continuation learned

Last round's drain-on-breaker-open was the primary defence. It isn't any more — the continuation stops the buffer filling in the first place, and the drain only matters for a buffer that was *already* full at session start, which LOG8 proved really does happen.

It has also been taught to skip devices the collection path has already found do not serve queued messages. That is a direct response to LOG8's own six silent probes: there is no point spending them again.

### What got built (all new/changed files in commit `efa1a05`)

Client/server split exactly as architecture rev 5 specifies: **all MVR/GDTF/zip/XML parsing happens in the browser**; the server only ever sees already-normalized patch-entry JSON.

- **`mvrzip.js`** — hand-rolled, lazy, zero-dependency ZIP reader. Generic over any `ArrayBuffer`/`Uint8Array`, so the same function opens the outer `.mvr` and, recursively, a `.gdtf` entry's bytes pulled out of it (a GDTF fixture-type file is itself a zip). Correctly reads the local file header's own filename/extra-field lengths to find each entry's real data offset rather than trusting the central directory's copies (the #1 bug in hand-rolled zip readers — verified against a hand-crafted archive where the two deliberately diverge). DEFLATE via the browser's native `DecompressionStream('deflate-raw')` — the one non-hand-rolled piece, and it's a platform API, not a third-party library. Throws a clear error on ZIP64 rather than silently misparsing (not supported — unlikely to matter for MVR-sized files, but explicit rather than silent).
- **`mvrparse.js`** — parses `GeneralSceneDescription.xml`: recursive `<Layer>` walk (arbitrary nesting), MVR's absolute-DMX-address → universe/startAddress conversion (`universe = floor((N-1)/512)+1`, `startAddress = ((N-1)%512)+1` — verified against an address crossing a universe boundary), lowest-`break` address chosen with a warning if additional breaks exist, best-effort `Position` from the nearest named enclosing `<Layer>`. 3D/`<Matrix>` geometry ignored entirely, per architecture rev 5.
- **`gdtfparse.js`** — parses a GDTF `description.xml`: per-`<DMXMode>` footprint as the max numeric `Offset` across its `<DMXChannel>`s (correctly excluding `Offset="None"` virtual channels), manufacturer/model → the same `"Mfr Model"` FixtureType convention `handlePatchAdopt` already uses. Also captures `<LogicalChannel>`/`<ChannelFunction>` data (offset, attribute, function name) even though nothing consumes it yet — forward-looking for a later function-aware rig check, not thrown away just because there's nowhere to put it in `patch.Entry` today. Full GDTF geometry-tree resolution (multi-instance repeated geometries) is explicitly out of scope — the literal per-mode channel list is used as-is, correct for the common case.
- **`mvrimport.js`** — orchestrates the three above end to end: opens the outer zip, finds `GeneralSceneDescription.xml` (case-insensitive last-path-segment match, doesn't assume exact casing/location), resolves each fixture's `GDTFSpec` against the archive (exact → `+.gdtf` → case-insensitive fallback), **caches parsed GDTF results by resolved entry name** (many fixtures commonly share one fixture type), matches the fixture's `GDTFMode` name against the GDTF's modes. Two fallback paths, neither of which aborts the whole import: an unresolvable GDTF reference, or a GDTF mode name that doesn't match anything in the resolved file — both degrade to a `footprint: 0` entry plus a warning, per Dom's established "assume an error, don't silently guess" pattern from the retry-storm fix two sessions ago.
- **`patchimport.go`** — `POST /api/patch/import`. `fresh` replaces the whole patch (mirrors `handlePatchAdopt`'s fresh branch). `merge` dedupes by **(Universe, StartAddress)** rather than adopt's ConfirmedUID (imported entries have no RDM identity at all — that only exists after a later Reconcile pass) — a match updates only the imported descriptive fields, never touching ID/ConfirmedUID/MatchState, so a re-import never disturbs an already-reconciled pairing. 5 new Go tests.
- **`patch.js`** — "Import MVR…" button, hidden file input, a preview panel (fixture count + warnings list, same never-color-alone convention as the collision banner) that must be explicitly confirmed (merge or fresh, worded exactly like the existing Adopt buttons) before anything reaches the server — Apply-to-confirm holds for import exactly as it does everywhere else in this screen.

### How this was built: delegated in 3 waves, per the project's architect/drone model

### Universe numbering base — display notation, never the wire

Dom's ask: Art-Net counts universes from 0, but the EN4s and Vectorworks both count from 1, and he wants to work in the notation his gear uses. His constraint, verbatim: *"this should not change the actual value sent — if our base is starting at 1 and I set a port to universe 1, actually send a 0."*

Implemented as `Settings.UniverseBase` (0 or 1, default 1) with the conversion in exactly one place — `UI.formatUniverse`/`UI.parseUniverse` in `ui.js` — applied at the presentation boundary only. ### MVR import stored every fixture one universe too high — found, fixed, and migrated

**The bug:** MVR numbers universes from 1. `mvrparse.js` faithfully computed `universe = floor((N-1)/512)+1` to match MVR's own convention — and `mvrimport.js` then passed that 1-based number straight through as `entry.universe`, which the server stores as the canonical **0-based** port address. Every MVR-imported fixture was therefore stored one universe high on the wire. Hand-entered and adopted-from-RDM entries were always correct; only imported ones were wrong. This shipped in `efa1a05` and survived that phase's real-file validation, because that validation checked fixture counts, footprints and collisions — all of which are correct — but never asked which universe the fixtures would actually be *driven* on.

Surfaced only because the numbering-base work forced a survey of what "universe" means at each layer. Worth remembering: the off-by-one was invisible while every layer was examined in isolation and obvious the moment one helper had to reconcile them.

**Fixed** so import emits canonical 0-based, with the MVR-1-based → canonical-0-based conversion commented heavily at the conversion site. Verified by hand against the real corrected show file: MVR absolute address 10535 → canonical universe 20, start 295, displayed "universe 21 / 295" at Dom's default base — matching Vectorworks.

**Migration — the interesting decision.** Dom chose "fix and migrate my existing patch." But `patch.Entry` carries **no provenance field**, so an imported entry is indistinguishable from a hand-entered one, and a blind shift-everything-down-one would corrupt every entry that was never wrong. Rather than invent a provenance field retroactively or guess, the correction is an explicit user-aimed action in the bulk editor — "shift selected down one universe" — which lists every selected entry's exact old→new universe in its confirm, refuses the **whole batch** (not a partial application) if any selected entry is already at universe 0, and clears the selection on success so a double-click is a no-op. Dom aims it at the entries he knows came from the import. On a live show network a silently mis-shifted address is expensive; an explicit action he points himself is the safer instrument even though it is more work for him. Flagged for a future decision: if provenance ever matters again, `patch.Entry` should carry an import-source field, which would make this class of migration mechanical.

### Devices screen: ports grouped by physical device

### Three root causes found while verifying, all fixed at the cause

The project's "diagnose, don't patch" rule earned its keep three times this session, twice on defects nobody had reported.

**1. `DetectCollisions` returned a nil slice.** `var findings []Finding` with no initialization marshals to JSON `null`, not `[]` — so a **collision-free** patch crashed the Patch screen outright (`Cannot read properties of null (reading 'length')`). Found when a freshly-imported clean 90-entry patch wouldn't render. A subagent had guarded the six client call sites with `|| []` and correctly declined to edit outside its boundary; the cause itself is now fixed (`make([]Finding, 0)`) with a test that asserts the **marshalled JSON equals `[]`** rather than merely that `len == 0`, since len==0 is true for nil and would have passed vacuously against the bug. Confirmed to fail against the unfixed code before being accepted. The client guards stay as defense in depth, with their comment corrected so it no longer describes an open bug. An audit for the same pattern found and fixed two more latent instances (`handlePatchReconcileFixAll`'s items, `toNodeJSON`'s ports) and explicitly cleared several others that use `omitempty` or are unreachable.

**2. Collision messages disagreed with the table about which universe.** Found by reading the live API rather than the UI: the Patch table showed two colliding fixtures in universe **6** while the collision banner said *"in universe 5"* — because the server built the sentence with the canonical number, which the client-side display layer never sees.
